# Web server

The Web UI is a FastAPI server (`web/server.py`) that serves the built Svelte app and a JSON API. This page covers how it runs jobs, stores presets and what it tells the frontend about models.

## Job queue

`WebRunner` (`web/web_runner.py`) runs every Web UI job on a single worker thread. Generation jobs are never refused for being second: `_submit_job` registers the job, publishes `job_submitted`, appends it to the FIFO queue and dispatches it, all under `_jobs_lock`, so the worker receives jobs in queue order. When the worker reaches a job, `_claim` takes it off the queue and publishes `job_started` (status `running`, `started_at`; `elapsed_secs` counts from here). A job removed with `cancel_queued`, `clear_queue` or `shutdown` is no longer queued, so the claim skips it even if its work item was already picked up; it ends with `job_cancelled` and `reason: "removed"`.

The *active* job is the claimed one or, between jobs, the head of the queue; every other unfinished generation job is *queued*, with a 1-based `queue_position`. `GET /api/jobs` and `/api/workspace` return them as `active_job` and `queued_jobs`, and a job is never in both. `DELETE /api/jobs/queue` removes the queued jobs and keeps the active one. Actions that need the model memory to themselves (manual prompt enhancement, saving a quantized copy, deleting models or LoRAs) still wait until no generation job is running or queued.

### Download lane

Downloads started from the Models page take a second path: `DownloadLane` (`web/download_lane.py`) runs them one at a time on its own thread. The lane never touches the job executor or the exclusive slot, so generation jobs are admitted while it downloads. Deleting a model, an enhancer model or a Hugging Face download is refused with 409 while a download touches its repo or folder (`_ensure_not_downloading` in `web/server.py`, using `DownloadFlights.conflict`). See [Model downloads](downloads.md). The lane also installs LoRAs (kind `lora`), see [Discover LoRAs](#discover-loras).

## Discover LoRAs

The Discover LoRAs routes serve the curated list (`utils/curated_loras.py`, see [The curated LoRA list](curated-loras.md)) and, once the user opts in, Hugging Face. The routes are in `server.py`; the logic is in `web/discover_api.py` (response assembly), `web/discover_hub.py` (what is read from the Hub), `web/hub_client.py` (the bounded reader), `web/lora_download.py` (names and the lane item), `web/lora_sources.py` and `web/lora_details.py` (where files came from and their triggers). Errors are `{"detail": "<text>"}` with the statuses below; a `detail` is always a sentence the UI can show.

**Every Hub read is anonymous and bounded.** `hub_client.http_fetch` never sends the user's token or any `Authorization` or `Cookie` header, builds every URL on `https://huggingface.co` on the server (a request value reaches a URL only through `validated_repo`, `validated_file` and `validated_revision`), follows redirects itself and only to `huggingface.co` and `*.hf.co`, and stops reading a body at its cap: 2 MB for a safetensors header, 8 MB for a JSON answer. `CachedFetch` keeps successful answers in memory for five minutes (128 entries and 16 MB of bodies in all, least recently used first; a body over 1 MB is not kept, and expired answers are dropped whenever the cache is used). `repo` must be `owner/name` without `..`; `file` must end in `.safetensors` and may not contain `..`, a backslash or a control character, nor start with `/` or `\`; a bad value is a 422 before the Hub is asked. Gated and private repositories are never listed and are refused as a detail or a download, and so are `not-for-all-audiences` repositories and, unless `ui.discover_content_filter` is `off`, repositories the content filter leaves out (see below). The server can be bound beyond localhost, so the Hugging Face routes also refuse (403) until the user has chosen to show Hugging Face LoRAs.

**Content filter.** The content filter (`web/listing_filter.py`) is a best-effort check on a repository's names, not a content rating. It looks at the repository ID, tags, trigger words and file names, splits them into words, and hides the repository when one uses a term from `web/listing_filter.json`. Some terms match only whole words, others also inside run-together names; the docstrings in `listing_filter.py` give the details. The term lists are base64-encoded to keep them out of casual reading; decode them to edit, and test with made-up terms. The routes build the filter from `ui.discover_content_filter` on each request: `on` (the default) hides repositories tagged `not-for-all-audiences` and those the terms match, `off` hides only the tagged ones. Gated and private repositories are always hidden. When a whole Hub page is filtered out, `list_adapters` reads up to two more before it answers.

| Route | Purpose |
|---|---|
| `POST /api/discover/settings` | Body and answer `{"hf_enabled": bool}`. The curated route reports the stored value. Stored as `ui.discover_huggingface` in the user config, so it is shared by every device that opens the app; `false` turns the results off again |
| `GET /api/discover/curated?family=&size=&version=` | The curated entries for a model, each with its state on this machine |
| `GET /api/discover/installed-thumbnails/{name}` | The preview image kept when the Hugging Face LoRA `name` was downloaded; 404 when none is kept |
| `GET /api/discover/hf?family=&size=&version=&q=&sort=&cursor=` | One page of Hugging Face LoRAs for the model's official base repository (403 until opted in) |
| `GET /api/discover/hf/repo?repo=` | One repository: files, card facts, previews and the name each file would save as |
| `GET /api/discover/hf/check?repo=&file=&family=&size=` | Which model a file was made for, from its header read by HTTP range |
| `POST /api/discover/download` | Start the download of a curated entry or a repository file; returns the lane item and the final name |
| `PUT /api/loras/{name}/trigger` | Set the trigger the user typed for an installed LoRA |
| `DELETE /api/loras/{name}` | Delete a LoRA and the record of its source; 409 while a job runs |

**Curated.** `GET /api/discover/curated` answers `{family, size, version, hf_enabled, entries}`. `size` (`4b`, `9b`) and `version` (`2.3`, `2.5`) narrow the entries as `curated_for_family` does and may be omitted; a family with no curated entries answers `entries: []`. Each entry has the curated-list fields `id`, `name`, `family`, `size_variant`, `version`, `display_name`, `author`, `description`, `section`, `what_it_does`, `workflow`, `repo`, `revision`, `file`, `size_bytes`, `trigger`, `weight`, `licence`, `non_commercial`, `downloads`, `platforms`, `note`, `previews` and `preview_videos`, and: `size_label`, `licence_label`, `model_card_url`, and the machine's state:

- `state`: `available`; `downloading` (a lane item is queued or running for it, carried as `download`); `installed` (a file of its name and exact size is in the LoRA folder); `name_taken` (that name belongs to a different file or another download, so Use would be refused; the drawer shows such an entry as not available, with no Delete file and no chip).
- `download`: the lane item JSON while `downloading`, else `null`.

**Hugging Face list.** `family` is required; `size` narrows Klein to one repository (without it both are listed); `version` (`2.3`, `2.5`) narrows LTX to the adapters of that version's repository (without it both are listed). A repository that is an adapter of several of the listed bases is listed once. `sort` is `downloads` (default), `likes`, `trending` or `newest`; `q` is at most 100 characters. A family without a base repository is a 422. The answer is `{items, next_cursor, base_models}`; pass `next_cursor` back as `cursor` for the next page, and `null` means the last page. A page can hold fewer rows than asked because gated, adult-tagged, filtered and fileless repositories are dropped. A row is `{repo, name, author, downloads, likes, files, licence, thumbnail, trending_score, created_at, updated_at, curated_id}`: `name` is the cleaned repository name, `files` counts the `.safetensors` files, `thumbnail` is a Hub URL or `null`, and `curated_id` marks a repository with a curated entry.

**Repository detail.** `GET /api/discover/hf/repo` answers `{repo, name, author, revision, downloads, likes, licence, licence_label, base_model, instance_prompt, previews, preview_videos, model_card_url, preselected, files, other_files}`. `revision` is the commit every later call pins; `base_model` is what the author declares; `instance_prompt` is the card's trigger words, comma-separated (`utils/lora_trigger.card_triggers`); `previews` are Hub resolve URLs (anything pointing elsewhere is dropped). `preselected` is the file to offer first: one marked recommended, final or best, else one without a step number, else the highest step. `files` are the choices (the preselected file and real variants) and `other_files` the training snapshots to fold. A file is `{file, size_bytes, size_label, sha256, step, marked, curated_id, save_as, renamed, state}`: `save_as` is the local name it would get (a slug of the repository name, with `-2`, `-3` when taken on disk or by a running download), `renamed` says the slug was taken, and `state` is `available`, `downloading` or `installed` (the same file from the same commit is already installed under that name). A taken name is therefore known before Use is pressed.

**Family check.** `GET /api/discover/hf/check` reads only the safetensors header of the file with two `Range` requests: the 8-byte length, then exactly that many bytes, so a header that would take the read past 2 MB is not read (the file must be one the repository lists) and answers `{status, family, size_variant, expected: {family, size_variant}}`. `status` is `match` (made for the asked model), `mismatch` (made for `family`/`size_variant`, which differ) or `unknown` (the header is unreadable, too large for the cap, or names no family).

**Download.** `POST /api/discover/download` takes `{"curated_id": "<id>"}` or `{"repo": "<owner/name>", "file": "<path>", "name": "<optional>"}` and answers `{name, status, renamed, item, trigger, trigger_source}`. A curated entry saves under its curated `name`; a repository file under `name` if given, else a slug of the repository name, numbered when taken. `status` is `queued` (a new lane item, in `item`), `running` (the same file is already downloading; `item` is that item, so two presses make one download) or `installed` (the same file is already there; `item` is `null`). `trigger` is the text to offer (the curated entry's, or the card's trigger words, comma-separated) and `trigger_source` is `curated` or `card`. Refusals come before any bytes move: 409 when a curated entry's name belongs to a different file or download, 403 for a repository file before the opt-in, 404 for an unknown id or a file the repository does not list, 422 for a bad value or a gated, adult-tagged or filtered repository, 502 or 503 when Hugging Face cannot answer.

**Progress.** The item is a lane item (`kind: "lora"`, `name` the local name, `label` `LoRA <name>`) and its progress, cancel and final states are those of `GET /api/models/downloads` and `POST /api/models/downloads/{id}/cancel`; see [Model downloads](downloads.md#model-downloads). The item adds `curated_id`, `source_repo`, `source_file`, `source_revision` and `size_bytes`. A `done` item means the file is installed and its source recorded; a `failed` one carries the reason in `message` (for example a SHA-256 mismatch) and left no file. The Models page **Import a LoRA** from Hugging Face (`POST /api/models/import-lora/hf`, body `repo_id`, optional `filename` and `name`) uses the same item and returns at once with `{status: "ok", tone, message, name, outcome, download}`; `outcome` is `queued`, `running` or `installed`, a typed `name` that is taken is a 409, and an unnamed import is saved under the file's stem, numbered when taken. It keeps the user's Hugging Face token, so a private repository they can open imports.

**Installed LoRAs.** The `loras` rows of `GET /api/workspace` and `GET /api/models` also carry `curated_id`, `title`, `trigger`, `trigger_source`, `source`, `hub`, `size_bytes` and `size_label`. `trigger_source` is `curated`, `card`, `header` or `user` (the order of trust, see [LoRA sources](app-database.md#lora-sources)) and `trigger` is the trigger words, comma-separated, or `null` when none is known; `source` is `{repo, revision, file, sha256, curated_id}` for a file the app downloaded, else `null`. `title` is the curated entry's display name, or the repository's name for a Hugging Face download, else `null`. `hub` is set for a Hugging Face download that is not a curated entry and holds what it kept: `{name, author, downloads, licence, licence_label, model_card_url, thumbnail_url}`, with `thumbnail_url` pointing at `GET /api/discover/installed-thumbnails/{name}` (null when no image was kept); it is how the Installed tab describes the file offline. `PUT /api/loras/{name}/trigger` takes `{"trigger": "<text>" | null}` and answers `{name, trigger, trigger_source, user_trigger}`; a typed trigger wins over every other source, and `null` or blank clears it. Deleting a LoRA also deletes its source row; while a generation job is running or queued the delete is refused with 409 and `detail` "Delete is off while a job runs: the job may be loading this file. Wait for all jobs to finish, then try again.".

**Memory estimate.** `POST /api/video/memory-fit` and `POST /api/extend/source` count a MiniMax H3 LoRA that is still downloading at the size its download expects (the curated entry's, or the Hub's), instead of refusing the missing file.

## Job log

`web/job_log.py` is the `jobs` component of the [app database](app-database.md): one row per finished job in `jobs_entries_v1`, ordered by `seq`. `server.py` builds it as `JobLog(app_db.app_db_path)`. `WebRunner` takes it as the `job_log` argument and writes nothing without one.

- **Which jobs.** Only image, video, audio and upscale jobs that started (`started_at` is set) are logged. A job removed from the queue never started, and `dummy` jobs are not generation jobs, so neither is logged.
- **Once only.** A job is logged when it first reaches a terminal status (`completed_at` still unset). A later terminal event changes the in-memory status but writes no second entry, so the log keeps the first outcome.
- **Where the write happens.** `_publish_event` copies the plain facts of the job under `record.lock` and writes last, after the subscriber fan-out and the release of the claim, holding no lock. Every logged terminal is published on the worker thread, so the write never blocks the event loop; the routes of the log are plain `def` and run in the threadpool. If a future change logs queue removals, the write must move off the loop.
- **Failures never reach the job.** Building the entry and writing it share one `try/except Exception` that only emits a `UserWarning`, so the terminal event, the claim release and the next queued job do not depend on the log.
- **Partial failures.** The record counts `generation_finished` events with `status: "failed"` (`failed_runs`) and keeps the last reason. A job that still ends `completed` or `cancelled` keeps that status, and the `failed` filter of `GET /api/jobs/log` matches it through `failed_runs`.
- **Storage.** Each row holds `job_id` and the entry's JSON text as `json.dumps(entry, ensure_ascii=False, default=str)` wrote it, so a listing returns what was written (key order, `100.0`). A listing reads every row and filters and pages with `page_entries` / `matches_status`. Each operation uses its own connection, writes run in `app_db.transaction`, and there is no lock. Rows are never trimmed; they stay until `delete` or `clear` removes them.
- **Best effort.** Two `ziv ui` servers on one data directory share the table safely. A server stopped while a job runs may exit before the worker writes that job's entry. A damaged database is quarantined whole and the log restarts empty, with the old rows kept in the `.corrupt-*` file.
- **Routes.** `GET /api/jobs/log` (50 per page, newest first, `status` filter), `DELETE /api/jobs/log/{job_id}` and `DELETE /api/jobs/log` are declared before the `/api/jobs/{job_id}/...` routes. Every storage failure, and a jobs schema newer than this ziv, reaches the routes as `JobLogError` and becomes a 500 with `Could not read or write the job log: <reason>`.
- **Tests.** The autouse `_isolated_app_db` fixture points the app database, and so the job log, at a temporary directory.

## Recent prompts

`web/recent_prompts.py` is the `recent_prompts` component of the [app database](app-database.md): one row per distinct mode, format, prompt, scene and negative prompt in `recent_prompts_entries_v1`, newest by `seq`. It is separate from the job log on purpose: the log writes a job only after it started and ended, truncates the prompt, and its Delete and Clear log would otherwise remove recents.

- **What is recorded.** `_generate_from_form` calls `_remember_prompt` after `POST /api/generate` accepted a job. `recent_prompt_entry` (pure) builds `{format, prompt, scene, negative_prompt, mode, used_at}` for an inline submit: `format: "text"` with the trimmed prompt, the scene for video and the negative prompt for images, or `format: "json"` with the trimmed `json_prompt` as `prompt`. It returns nothing for `prompt_source=file`, or when the prompt (or caption) and scene are both blank. A refused submit (409, 422) never reaches it. The text recorded is the one the form sent, so the user's own text in auto-enhance mode and the Enhanced text when it is used.
- **Audio.** An audio submit keeps its prompt (a song's style, the text of speech, a sound's description) under its kind as the mode (`music`, `speech` or `sound`), so each kind has a list of its own. A song also keeps its lyrics in `scene`; there is no negative prompt.
- **Dedupe.** The key is `(mode, format, prompt, scene, negative_prompt)`. Recording an existing one is an `INSERT OR REPLACE` that gives the row a new highest `seq`, so it becomes the newest and takes the new `used_at`. Nothing is capped or trimmed.
- **Routes.** `GET /api/recent-prompts?mode=image|video|music|speech|sound&q=` returns `{"entries": [...]}`: the newest 50 rows of that mode whose prompt or scene contains a non-blank `q`, ignoring case. `DELETE /api/recent-prompts?mode=image|video|music|speech|sound` removes the rows of that mode and returns `{"deleted_count": n}`. `mode` is required on both; any other value is a 422.
- **Failures.** They never reach the submit: `_remember_prompt` only emits a `UserWarning`, so the response of an accepted job is unchanged. A storage failure, and a schema newer than this ziv, reaches the routes as `RecentPromptsError` and becomes a 500 with `Could not read or write the recent prompts: <reason>`.

## Video upscale jobs

`POST /api/upscale` on a gallery video queues an `upscale` job whose context, submit response and snapshot carry `media_type: "video"` and `upscale_method` (`seedvr2` or `ltx`; image jobs leave both out). The method is the platform's `video_file_upscale_method()`, and the job card counts batches or steps by it. With SeedVR2, `upscale_api.plan_video_upscale` builds the request and `WebRunner.submit_video_file_upscale_job` runs it through `video_file_upscale_runner.run_video_file_upscale` after the same SeedVR2 download plan and load as the image upscale. With LTX (macOS), `upscale_api.plan_ltx_video_upscale` picks the LTX-2.3 model, prompt, seed, steps and the clip's LoRAs that still exist, and `WebRunner.submit_ltx_video_upscale_job` downloads and loads the model for upscale and runs `run_ltx_video_upscale`. Both share one job body. The runner builds the result in a hidden `.ziv-tmp-upscale-*` folder beside the source, which the gallery and `/media` never list or serve, and moves it into place at the end, so a quit or a failure leaves nothing. The result embeds the source's config through `provenance.build_video_upscale_payload`, with `workflow: "upscale"` and a `source` block that follows back to the original.

## Audio jobs

`POST /api/generate` with `mode=audio` and `POST /api/generate/plan` share `_parse_audio_job`; `_submit_audio_job` queues the result with `WebRunner.submit_audio_request_job` (`job_type="audio"`, exclusive). The plan route lists the audio model as one download part with its licence records.

**Plan without files.** The Workspace posts the generate form to `/api/generate/plan` with each upload as an empty part that keeps its field and file name (`planForm`), then posts the real form once to `/api/generate`. `_generate_plan_from_form` swaps every upload for a `PlannedUpload` before it parses, so the plan route never reads or saves a file. The file helpers still check extensions, so the user is never asked to approve a download for a job that cannot run; what needs a file's content is left to the submit.

- **Form.** The field names are the ones Copy CLI reads (`frontend/src/lib/state/cliCommand.ts`, with the shared fixture `tests/fixtures/audio_cli_cases.json`): `workflow` (`music`, `speech` or `sound`), `model`, `prompt`, `lyrics`, `seconds`, `tempo`, `key`, `speaker`, the five delivery fields (`emotion`, `manner`, `pace`, `pitch`, `expressiveness`), `sound_type`, `voice_path` or the `voice_file` upload, `voice_text`, `voice_consent`, `seed` and `runs`. A text the enhancer wrote adds `prompt_input` (the user's own text, which may be empty) and `enhance_record` (JSON, see below). A field that belongs to another kind than the model's is ignored; a blank `tempo`, `key` or `seconds` is Auto.
- **The request is the CLI's.** `web/audio_job.audio_request_from_fields` builds the `AudioGenerationRequest` the way `ziv audio` does, using the same checks in `utils/audio_request.py`, so a form and a command word their refusals alike. Refusals are a 422.
- **Consent.** A one-off voice recording needs `voice_consent`, unless it is a gallery take made without a reference voice (`audio_voice.voice_needs_consent`). That tick is checked and never saved: the job's recorded settings drop it, so a loaded or retried job comes back unticked. A saved voice needs no tick: its consent is in its record (see [Saved voices](#saved-voices)). The form names it as `saved_voice` (a slug; an unknown one is a 422), which overrides the recording, `speaker` and delivery fields. The job's recorded settings keep the library path as `voice_path`, which is how a take shows the voice's name and Reuse gives `saved_voice` back.
- **Events.** The runner is `audio_runner.run_audio_batch`. Besides the events of the other runners, a job publishes `model_downloading` (`mode: "audio"`) and `model_loading`, and per take any number of `audio_progress` events (`phase`, `step`, `total` or `null`, `part`, `n_parts`, `elapsed_secs`, `eta_secs`). A Stop is honoured at every step, also while the model loads: the load polls a Quit check between tensors. A take that fails ends the job `job_failed`; the takes before it are saved. The job's context carries `media_type: "audio"` and no `width` or `height`.

The workspace payload (`GET /api/workspace`) lists `audio_models`, one row per preset that runs on this machine, in config order (`web/audio_models.py`): `id`, `label`, `kind`, `limits`, `instrumental_sections` (a music model's section list), `licences`, `downloaded` and `memory_fit`. The workflow contract lists `music`, `speech` and `sound` only for kinds with a runnable model, so a config with no audio preset leaves the Audio tab hidden.

### Audio text enhancement

`POST /api/prompt/enhance` takes `mode: "audio"` beside `image` and `video`; it shares the endpoint's NDJSON stream, its Fast/Smart choice (`enhance_model`) and its admission: a running job or another enhancement gives a 409, because the enhancer and the audio models never share the GPU. `web/audio_enhance.py` owns the audio side. The rules of each task live in `utils/prompt_enhance_audio.py` (the caption rewrites `sound` and `style`, written by the preset's backend family) and `utils/audio_writers.py` (the writer tasks `lyrics`, `script` and `fill`; `speech_realign.py` holds the script helper's word matching). A `task` that is not in `audio_enhance.ENHANCE_TASKS` is a 422.

**Request.** `task`, `model` (the audio preset id, which must make the kind), `kind`, `prompt`, `settings` and `context`. A bad value is a 422 in the user's words.

| Task | Does | `kind` | `prompt` | `settings` |
|---|---|---|---|---|
| `sound` | Rewrites a Sound prompt | `sound` | The prompt, 1 to 1,000 characters | `space`, `distance`, `over_time`, `movement`, `note` |
| `style` | Rewrites a Music style | `music` | The style, 1 to 1,000 characters | `genre`, `music_mood`, `instruments`, `without`, `singer`, `production`, `note` |
| `lyrics` | Edits a song's lyrics; the model must take lyrics | `music` | The song as the Lyrics box holds it, up to 4,000 characters | `{action: "improve" \| "write", improve: [...], note, section}` |
| `script` | Edits a speech text | `speech` | The Text with its marks, up to 4,000 characters | `{actions: ["fit", "delivery"], seconds?, pace?}` |
| `fill` | Writes several fields from an idea | `music` (default) or `speech` | The idea, up to 1,000 characters | `{fields: [...]}` |

`context` holds `lyrics` and `text`, `style`, `instrumental`, `tempo`, `key`, `seconds` and `sound_type`; each task reads what it needs. An axis of the other kind, an unknown slug or an instrument in both Instruments and Without is a 422.

- **`lyrics`.** `improve` lists `tighten`, `fit`, `rhymes` or `simpler` (none is a general polish; `fit` is for the whole song). `section` is the index among the `[section]` tags from 0, `null` for the whole song; a `write` needs a section with no words in a song that has some. The `done` frame's `fields.lyrics` is always the whole song. The lyrics text is not a record and is not saved with the take.
- **`script`.** `actions` lists each of `fit` and `delivery` at most once, and runs fit first; `seconds` is a whole number from 3 to 600 and required with `fit`; `pace` is one of the Pace values (default `normal`). With both actions, one request makes one `done` frame and one record. `delivery` never changes the script's words. The `done` frame's `fields.script` is the whole script.
- **`fill`.** `fields` lists the ones the client found empty: `style`, `tempo`, `key`, `lyrics` for music (`lyrics` needs a model that takes lyrics) and `vibe`, `text` for speech. One enhancer call answers them all, and each is validated on its own; fields still missing are named in the `warning`. The `done` frame's `fields` holds each valid field as text (`tempo` as the number, `key` as the ABC id, `vibe` as the Vibe id).

**Frames.** `status` frames as for images. `text` frames are `{type, task, text, fields}` and the `done` frame is `{type, task, fields, clamped, model, warning?}`: `fields` maps each written field to its text (`prompt` for `sound`, `style` for `style`). `model` is the enhancer that wrote it (`REPO[@REVISION]`), which the client sends back as part of `enhance_record`. A changed quoted text is a `warning` on the `done` frame. A writer whose answer left the text as it was ends in `{type: "error", detail, no_change: true}`, so the client shows a note instead of an error.

**Saved record.** `enhance_record` is `{settings, model, tier, format: "text", task}`, where `settings` holds only the options that are not defaults. For the script helper `task` is `script` and `settings` is what it did; the Written text is the take's `prompt` and the user's own text its `prompt_input`. `_parse_audio_job` reads it with `parse_enhance_record(mode="audio")`: a record that cannot be read is dropped with a warning instead of failing the take. A take with a record saves `prompt_input` (even `""`) and `enhance` in its FLAC settings; Reuse gives back `prompt` (the user's own text), `enhanced_prompt` and `enhance` (the record as JSON). Fill in writes into the user's own fields and leaves no record.

`prompt_enhancer.audio_matrix` lists the audio axes (`key`, `label`, `multi`, `kind`, `vocal`, `options`, `default`) for the Workspace.

### Audio models on the Models page

`GET /api/models` lists `audio_models` after `video_models` (`web/audio_inventory.audio_inventory_rows`), empty when the metadata has no audio model. A row has `name`, `label`, `kind`, `licences`, `downloaded`, `download_needed`, `memory_fit` (GPU only), `delete` and `disk_size_label`.

- **Download.** `GET /api/models/download/plan` and `POST /api/models/download` take `kind=audio` and the model id.
- **Delete.** `DELETE /api/audio-models/{name}` removes the model's repositories from the Hugging Face cache. It is refused (409) while a job runs or a repository is downloading, and is a 404 for a model with nothing on disk.
- **Unused downloads.** The repositories of every audio model count as used, so `find_other_downloads` never lists them under Other downloads.

## Saved voices

`web/voices.py` holds the logic of the `/api/voices` routes and `utils/voice_library.py` the store: `<data dir>/voices/<slug>.wav` and a `<slug>.yaml` record. The slug is made once from the name (`utils/slug.slugify`, the rule settings presets use) plus a short random hex suffix (`anna-3fa2`, or `voice-3fa2` for a name with no ASCII letters), so it is unique and effectively never reused; a rename keeps it. Names are unique ignoring case.

- **Consent lives in the record only.** `audio_voice.consent_for_saving(path, ticked)` decides it when a recording is saved: `given` for a tick, `not_needed` only for a speech take of this app made without a reference voice, otherwise `CONSENT_REQUIRED`. A designed voice is always `not_needed`. The routes never return the consent or the path.
- **Nothing is written under the output folder.** The routes serve a voice's WAV by slug only. A recording is probed against the model's voice limits before it is decoded, so a long file is refused, never cut.
- **Delete is a 409 while any job is active**, because the job may be reading the voice.

### Voice design jobs

A design run is its own job, because it makes candidates, not takes: `POST /api/voices/design` queues `WebRunner.submit_voice_design_job` (`job_type="voice_design"`, exclusive), after `POST /api/voices/design/plan` has listed the VoiceDesign checkpoint in the usual download plan. Its context has `workflow: "voice_design"` and no `settings`, so it is not logged, cannot be loaded or retried, and offers Cancel only. The runner is `audio_runner.run_voice_design`.

Candidates are not outputs. They live in `<data dir>/voice-design/` (`utils/voice_candidates.py`), outside the output folder, so no gallery, `/media` or job result lists them. A run adds a batch and never replaces an earlier one. `GET /api/voices/design` returns the batches and `unpicked`, the count of saveable, unsaved candidates made since the last save or Clear voices; clearing is a 409 while a design job is queued or running.

## Audio in the gallery

`AUDIO_EXTENSIONS` (`.flac`, `.wav`, `.mp3`, `.m4a`, `.ogg`) are gallery media: `/media` serves them with ranges so a player can seek, and `GET /api/gallery?filter=audio` lists only them. `_read_audio_facts` makes one ffprobe call per file for the embedded settings, duration, channels and sample rate, and never decodes it. The 100 waveform peaks are computed lazily: `GET /api/gallery-peaks?id=<asset id>` decodes the file on the first request and stores the result in the file's index row, so later requests and listings decode nothing; the asset JSON carries `peaks: null` until then. A take a job just made carries its peaks in its `generation_finished` asset. The asset JSON (`web/gallery_audio.py`) adds `kind`, `model_label`, `duration`, `peaks`, `channels`, `sample_rate`, `has_reference_voice`, `lyrics`, `cut` and `parts`, with `null` `upscale` and `extend` blocks. A file with this app's settings is reusable; its Reuse URL never carries the consent. `voice_name` is the name of the saved voice the take followed while that voice exists, else `null`, matched by the slug of the take's library path (`voice_slug_for_path`). Reuse gives `saved_voice` (the slug) for a take whose recording is in the voices folder, also once the voice is deleted; any other recording comes back as `voice_path` and `voice_text`. A file without them lists and plays but has no Reuse (`has_reusable_config: false`).

## Projects

A project is a folder directly under the output root; there is no registry. `web/projects.py` owns the rules: `list_projects(root)` returns the real folders (no files, symlinks or dot-prefixed names) sorted by `casefold`, `create_project(root, name)` applies the creation rules, and `asset_project(asset_id)` is the first segment of a multi-segment ID that doesn't start with a dot, else `None`.

| Route | Purpose |
|---|---|
| `GET /api/projects` | `{"projects": [{"name", "path"}]}`; clients never join paths |
| `POST /api/projects` | Body `{"name"}`. 422 for a name the creation rules refuse; 409 for a duplicate ignoring case |
| `GET /api/gallery?project=<name>` | The usual page, limited to assets whose `project` is the name; blank or absent means everything |
| `GET /api/gallery?filter=no_project` | The files in no project. `NO_PROJECT_FILTER` is a value of `filter` beside `image`, `video` and `audio`, not a project name, because a folder can be named anything. Empty with a `project` |
| `POST /api/gallery/move` | Body `{"asset_ids": [...], "project": str \| null}` (`null` is the top of the output folder). Answers `{"moved": [{"from", "asset"}], "failed": [{"id", "detail"}]}`; 422 for an invalid `project` |

Gallery asset JSON carries `project` (`str` or `null`), derived from the ID.

**Two checks on a name.** `create_project` applies the full creation rules, the same on every platform. `project_dir(root, name)` (saves and moves) only requires one plain segment, with no leading dot, backslash or NUL, so an existing folder the creation rules would refuse (such as `what?`) still works.

**Root and save folder are separate.** Generate and plan requests take an optional `project` form field. In `_parse_image_job`, `_parse_video_job` and `_parse_audio_job`, `args.output` (and an audio job's `output_dir`) is the save folder, `_project_save_dir(form, root)`: the project's folder, or the root when the field is blank. Uploads, staging, reference resolution and the job context's `output_dir` always use the root, because asset IDs and `/media` URLs are relative to it. `project` is not recorded in a file's settings (`_submitted_settings` skips it). The folder a job really saves into is the context's `save_project`, in the submit response and every job snapshot.

**Made-from outputs.** An upscale saves beside its source and carries that folder's project. `output_source_folder(root, source_path)` (`web/gallery.py`) returns an Extend source's parent when the source is an asset under the root, else `None`; `_parse_video_job` saves an extension there and otherwise in the picked project.

**Move.** `move_gallery_assets(output_dir, asset_ids, project)` handles each file on its own and returns `MoveResult(moved, failed)`; a file already in the target is in neither list. Each file is `os.replace`d to the next free name from `unique_output_path` (`utils/filename.py`); the check and the rename are not atomic, which the single-user, local design accepts. A move keeps mtime, flattens sub-folders and leaves `_preupscale` companions behind. `GalleryIndex.rename` then re-keys the index rows (see [Gallery index](app-database.md#gallery-index)). Source links in upscales and extensions are not rewritten.

## File browser previews

Purposes with a `preview` kind (`BrowsePurpose.preview` in `web/path_browser.py`: images, audio tracks, source videos) get four routes, with the logic in `web/browse_media.py`:

| Route | Returns |
|---|---|
| `GET /api/browse/preview?purpose&path[&size=large][&frame=last][&at=SECONDS]` | A WebP of an image or a video still, 384 px (768 with `size=large`). `at` picks the frame a second lies in; it is video-only, never negative, and not combined with `frame=last` |
| `GET /api/browse/info?purpose&path` | JSON facts: pixel size, length, format, waveform peaks. A video's facts are `width`, `height`, `fps`, `frames`, `seconds` and `start` |
| `GET /api/browse/sprite?purpose&path` | A video's contact sheet: one JPEG |
| `GET /api/browse/media?purpose&path` | The audio or video file, with range requests |
| `GET /thumbs/{asset_id}` | The 768 px WebP of a gallery image or video, confined like `/media` |

They only serve regular files with an extension the purpose accepts. Images are re-encoded without metadata. Pictures are cached in `<data dir>/cache/browse`; the picker routes refuse cross-site fetches where the browser sends `Sec-Fetch-Site`.

### Video frames

One rule turns a time in a clip into a frame, in `utils/video_point.py`: `frame_at(t) = clamp(floor((t - start) * fps + 1e-3), 0, frames - 1)`. `start` is the seconds from the file start to the first video frame (`VideoProbe.stream_offset`, which audio priming can make non-zero) and `frames` is the count the info route reports. `frame_seek_seconds(frame)` is half a frame before the frame, so `ffmpeg -ss` before `-i` decodes that frame first. `frontend/src/lib/state/framePoint.ts` applies the same rule; both are checked against `tests/fixtures/frame_point_cases.json`, so change them together. A clip is assumed to have a constant frame rate.

- **Preview `at`.** The time is snapped as above and goes into the cache key and the ETag, so a time that is not exactly a frame's still names that frame.
- **Sprite.** `utils/video_sprite.py` builds one JPEG per clip: an 11 x 11 grid of 160 px tiles. A clip of 121 frames or fewer has a tile per frame; a longer one has 121 evenly spaced tiles, and the tiles after the last are black. It is built on the first request and cached like a preview; a sheet that cannot be built is a 404 and is not cached.
- **Colour.** `frame_color_filter` in `utils/video_frame.py` is the one place that decides how a frame is converted to RGB: a clip with no colour matrix tag is read as BT.709, which is what a player shows, and a tagged clip follows its tag. Every video still and the sprite use it.

`POST /api/video/frame` takes `{"path": ..., "time": SECONDS}` for a host-local video and saves the frame that second lies in as a full-size, upright PNG at `.web_uploads/<sha256 of the PNG>/<clip>_<t>s.png` under the output folder, where `t` is the frame's own time to one decimal; the Gallery does not list `.web_uploads`. It answers `{"path"}`. A missing file is a 404, a bad path or time, an unreadable clip or a missing ffmpeg is a 422, and a failed ffmpeg is a 500 with ffmpeg's message. The logic is `web/video_frame_api.py`; the route shares the trust model of `/api/extend/source`.

### Extending from a point

An Extend job takes an optional `extend_from` form field: a time in the source clip, in seconds. `_parse_video_job` snaps it with `utils/video_cut.extend_cut_point`, which keeps the frame the time lies in as the last kept frame. A time at or past the last frame keeps the whole clip and sets no cut; a point that keeps fewer than 25 frames, or a negative, non-finite or non-numeric one, is a 422. The field is ignored for any other workflow. The parse only validates: it sets `args.extend_cut` (an `ExtendCut`) and writes no file, so `POST /api/generate/plan` stays free of files. `POST /api/extend/source` reports `video_start`, so the Extend bar can name a frame on the clip's clock.

The cut is made when the job runs. `WebRunner._run_video_request` and the CLI wrap the model load and the batch in `applied_extend_cut(args)`, after preflight and downloads. On entering the block it makes one `.ziv-tmp-cut-<pid>-*` folder in the save folder (creating it if missing), cuts the kept frames into it with one ffmpeg call (picture re-encoded at crf 12 with the source's colour tags, sound cut to the kept length), and checks the cut file holds exactly the kept frames at the source's size, or the job fails before the model loads. While the block runs, `args.extend_source` is a source rebuilt from the cut file that keeps the original's recorded scene, prompt, model, LoRAs and audio track, with `audio_track_end` moved back by the removed frames. The folder is removed and the original source put back when the block ends, whether the job finished, failed or was stopped. After a hard kill, the sweep before the next cut removes a `.ziv-tmp-cut-*` folder whose process no longer exists; a folder of another running process is left. The original file is never touched.

The output records `source_video` as the original clip and `extend_from` as the snapped time of the last kept frame, so `frame_at` returns the cut frame from it; `frame_count` is the kept frames plus the new ones. The Gallery reads `extend_from` at listing and adds it to an extension's Reuse parameters. When the clip followed an audio track, Start at moves back by the removed frames (`moved_track_end`): the CLI applies it itself, and a Web client sends the moved value as the track's start.

## Reference images

An image job takes references on top of its start image (`image_path`). The start image and last frame controls are listed on both workflows of a mode (`txt2img` and `img2img`, `txt2vid` and `img2vid`), so the Images section shows the same way in each. No workflow clears `image_path`, `end_image_path` or `image_strength`, because a tab change must not drop an image. The job's `workflow` is derived from the inputs it resolved (a start image or first frame makes it `img2img` or `img2vid`, whatever workflow the form posted), so the history and the job log record what ran; a posted `img2img` or `img2vid` without an image is refused. The Workspace sends `image_path` and `image_strength` only when the tab's start image is set and the model takes one, and `end_image_path` only with a first frame.

The Workspace form sends the references as one repeated `reference` field, one value per row in prompt order: an uploaded file, or the text path of an image on the host. One field keeps the rows numbered as the prompt refers to them ("image 1", "image 2"), which two separate upload and path fields could not. `_resolve_reference_images` saves uploads like the start image: each is checked and named by the SHA-256 of its content (`.web_uploads/<hash>.<ext>`), and a file already there is left as it is. An audio track upload keeps its own name, cleaned of unsafe characters, under that hash (`.web_uploads/<hash>/<name>`), so the Workspace can show it. `POST /api/audio-track/inspect` takes `{"path": ...}` and returns `{"seconds", "name"}` for a host-local audio file; a file that cannot be read is refused with 422. It also checks paths with `utils/references.py`; and `_validate_model_capabilities` refuses references for a model whose `max_reference_images` is 0 or below the count. The job's recorded settings replace `reference` with `reference_path`, the resolved files in order, which is also the name the Workspace URL and Reuse use (repeated).

A gallery image's Reuse URL names its recorded references as repeated `reference_path`, as recorded: the gallery does not check that the files exist. The Workspace keeps a row whose file is gone, marked missing, instead of dropping it, because dropping it would renumber the prompt. `image_model_defaults` carries `max_reference_images`, and the workflow contract lists the `references` controls on the image workflows only. `POST /api/references/check` takes `{"paths": [...]}` and answers `{"missing": [...]}` with the paths that are no longer files; the Workspace calls it on load, after anything that loads settings (Reuse, Load settings, a settings link) and after it deletes an image a row uses, to flag lost rows. It checks every slot path, not only the references: the start image, the first frame and the last frame too.

## Settings presets

Presets are a Web UI feature; the CLI does not know them. A preset is one YAML file, `<data dir>/presets/<mode>/<slug>.yaml` (`mode` is `image` or `video`), with the top-level keys `name`, `model` (or null) and `settings`; the folder decides the mode, so the file does not repeat it. `web/presets.py` owns the format, the slug rules and the store (writes under one lock with `write_text_atomic`).

- **Settings.** The `settings` keys are the Workspace form field names. Unknown keys are ignored when reading and writing, and missing keys count as not set. Prompt, seed, images and the workflow are never stored.
- **Routes.** `GET /api/presets` lists both modes sorted by name and skips invalid files. `POST /api/presets` creates one: the server derives the slug from the name and answers 409 when it is taken. `PUT /api/presets/{mode}/{slug}` overwrites (a `mode` in the body is ignored), `POST /api/presets/{mode}/{slug}/rename` renames, `DELETE /api/presets/{mode}/{slug}` removes; an unknown mode or a malformed slug in the path is 422. `POST` takes the mode in its body. Names and slugs are unique within a mode, so image and video presets can share a name.
- **Web apply.** `draft.applyPreset(ctx, preset)` (helpers in `lib/state/presets.ts`) applies a preset the same way in every workflow: keys outside the preset (prompt, seed, images, workflow) are untouched, and the capability gates re-run so the new model clears what it cannot use, as a manual model switch does. A model or LoRA that is not installed is skipped without a message.
- **Deselect.** A mode switch, Reset, and an extend or reuse that loads a source's settings clear the applied preset; a preset can be picked again afterwards. The applied slug is a single value in the draft (not per mode); it moves on rename and clears on delete.
- **UI parts.** `PresetMenu.svelte` is the toolbar control and, on a phone, the sheet behind the first chip; `PresetNameDialog.svelte` is the Save as and Rename dialog; `lib/state/presets.svelte.ts` is the list store.
- **Tests.** An autouse fixture in `tests/conftest.py` points the presets folder at a temporary directory, so no test reads or writes the real one.

## Model inventory

A built-in image model can declare its image family in its metadata entry with `family` (for example `ideo: ideogram4`). The Web UI inventory and workspace bootstrap consult this declared family as an offline fast-path, so a known alias is surfaced without the network `detect_image_model` round-trip that a bare Hugging Face repo id would otherwise require. Content-based detection for arbitrary local model directories is unaffected; only aliases with a declared family skip detection.

The `name` of a model's entry in `model_metadata.yaml` is how the Web UI names it; `utils.model_metadata.model_display_name(name)` returns it, or the id itself when the model has no entry. The server fills `label` on the workspace model options, the Models rows, download plans (and so the lane items) and `model_label` on a job's context and snapshot. The alias stays the id in every API field, CLI flag, prompt file and recorded setting; only the Workspace picker, job card, queue row and Models page show the name.

The `download_size` of an image model's entry (a plain value, or a `darwin` / `win32` / `linux` map) is its one-time download size; the workspace payload carries this platform's value as `download_size_label` on the image options (`utils.model_metadata.model_download_size_label`). It is entered from a dry-run download plan against an empty cache, so update it when a model's repo or files change. The first-run dialog (`FirstRunDialog.svelte`) opens when every image model is not downloaded, no image download is queued or running and `ui.first_run_skipped` is not set. `first_run` in `config.yaml` names the models it recommends: `web/first_run.recommended_first_run_model` returns `large_model` when the machine's memory (Mac unified memory, CUDA total VRAM) is at least `min_memory_gb` within 5%, else `small_model`, and the workspace payload's `first_run` block carries that and the skip flag. `POST /api/first-run/skip` writes `ui.first_run_skipped` to the user config; it is not a writable config field.

A built-in model's source is the upstream repo when it is ungated, otherwise a mirror whose weight files match upstream's sha256.

Per-model Web UI capability flags — `supports_img2img`, `supports_upscale`, `supports_scheduler`, `supports_json_prompt`, `supports_first_sigma`, `dimension_min`, `dimension_max`, and `dimension_step` — are data-driven: they originate in the `image_families` entries of the model metadata (read by `utils.model_metadata.model_capabilities`), flow through `resolve_defaults`, and are emitted into the SPA's `ImageModelDefaults`. Families that do not set them inherit permissive defaults (img2img, upscale and scheduler enabled, JSON caption and first-sigma disabled, `16`/`null`/`16` dimension bounds), so gating is centralized in the metadata rather than branching on family in the web layer.
