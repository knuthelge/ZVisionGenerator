# Web server

The Web UI is a FastAPI server (`web/server.py`) that serves the built Svelte app and a JSON API. This page covers how it runs jobs, stores presets and what it tells the frontend about models.

## Job queue

`WebRunner` (`web/web_runner.py`) runs every Web UI job on a single worker thread. Generation jobs are never refused for being second: `_submit_job` registers the job, publishes `job_submitted`, appends it to the FIFO queue and dispatches it, all under `_jobs_lock`, so the worker receives jobs in queue order. When the worker reaches a job, `_claim` takes it off the queue and publishes `job_started` (status `running`, `started_at`; `elapsed_secs` counts from here). A job removed with `cancel_queued`, `clear_queue` or `shutdown` is no longer queued, so the claim skips it even if its work item was already picked up; it ends with `job_cancelled` and `reason: "removed"`.

The *active* job is the claimed one or, between jobs, the head of the queue; every other unfinished generation job is *queued*, with a 1-based `queue_position`. `GET /api/jobs` and `/api/workspace` return them as `active_job` and `queued_jobs`, and a job is never in both. `DELETE /api/jobs/queue` removes the queued jobs and keeps the active one. Actions that need the model memory to themselves (manual prompt enhancement, saving a quantized copy, deleting models or LoRAs) still wait until no generation job is running or queued.

### Download lane

Downloads started from the Models page take a second path: `DownloadLane` (`web/download_lane.py`) runs them one at a time on its own thread. The lane never touches the job executor or the exclusive slot, so generation jobs are admitted while it downloads. Deleting a model, an enhancer model or a Hugging Face download is refused with 409 while a download touches its repo or folder (`_ensure_not_downloading` in `web/server.py`, using `DownloadFlights.conflict`). See [Model downloads](downloads.md). The lane also installs LoRAs (kind `lora`), see [Discover LoRAs](#discover-loras).

## Discover LoRAs

The Discover LoRAs routes serve the curated list (`utils/curated_loras.py`, see [The curated LoRA list](curated-loras.md)) and, once the user opts in, Hugging Face. The routes are in `server.py`; the logic is in `web/discover_api.py` (response assembly), `web/discover_hub.py` (what is read from the Hub), `web/hub_client.py` (the bounded reader), `web/lora_download.py` (names and the lane item), `web/lora_sources.py` and `web/lora_details.py` (where files came from and their triggers). Errors are `{"detail": "<text>"}` with the statuses below; a `detail` is always a sentence the UI can show.

**Every Hub read is anonymous and bounded.** `hub_client.http_fetch` never sends the user's token or any `Authorization` or `Cookie` header, builds every URL on `https://huggingface.co` on the server (a request value reaches a URL only through `validated_repo`, `validated_file` and `validated_revision`), follows redirects itself and only to `huggingface.co` and `*.hf.co`, and stops reading a body at its cap: 2 MB for a safetensors header, 8 MB for a JSON answer. `CachedFetch` keeps successful answers in memory for five minutes (128 entries and 16 MB of bodies in all, least recently used first; a body over 1 MB is not kept, and expired answers are dropped whenever the cache is used). `repo` must be `owner/name` without `..`; `file` must end in `.safetensors` and may not contain `..`, a backslash or a control character, nor start with `/` or `\`; a bad value is a 422 before the Hub is asked. Gated, private and `not-for-all-audiences` repositories are never listed and are refused as a detail or a download. The server can be bound beyond localhost, so the Hugging Face routes also refuse (403) until the user has chosen to show Hugging Face LoRAs.

| Route | Purpose |
|---|---|
| `POST /api/discover/settings` | Body and answer `{"hf_enabled": bool}`. The curated route reports the stored value. Stored as `ui.discover_huggingface` in the user config, so it is shared by every device that opens the app; `false` turns the results off again |
| `GET /api/discover/curated?family=&size=&version=` | The curated entries for a model, each with its state on this machine |
| `GET /api/discover/installed-thumbnails/{name}` | The preview image kept when the Hugging Face LoRA `name` was downloaded; 404 when none is kept |
| `GET /api/discover/hf?family=&size=&version=&q=&sort=&cursor=` | One page of Hugging Face LoRAs for the model's official base repository (403 until opted in) |
| `GET /api/discover/hf/repo?repo=` | One repository: files, card facts, previews and the name each file would save as |
| `GET /api/discover/hf/check?repo=&file=&family=&size=` | Which model a file was made for, from its header read by HTTP range |
| `POST /api/discover/download` | Start the download of a curated entry or a repository file; returns the lane item and the final name |
| `PUT /api/loras/{name}/trigger` | Set the trigger the user typed for an installed LoRA |
| `DELETE /api/loras/{name}` | Delete a LoRA and the record of its source; 409 while a job runs |

**Curated.** `GET /api/discover/curated` answers `{family, size, version, hf_enabled, entries}`. `size` (`4b`, `9b`) and `version` (`2.3`, `2.5`) narrow the entries as `curated_for_family` does and may be omitted; a family with no curated entries answers `entries: []`. Each entry has the curated-list fields `id`, `name`, `family`, `size_variant`, `version`, `display_name`, `author`, `description`, `section`, `what_it_does`, `workflow`, `repo`, `revision`, `file`, `size_bytes`, `trigger`, `weight`, `licence`, `non_commercial`, `downloads`, `platforms`, `note`, `previews` and `preview_videos`, and: `size_label`, `licence_label`, `model_card_url`, and the machine's state:

- `state`: `available`; `downloading` (a lane item is queued or running for it, carried as `download`); `installed` (a file of its name and exact size is in the LoRA folder); `name_taken` (that name belongs to a different file or another download, so Use would be refused; the drawer shows such an entry as not available, with no Delete file and no chip).
- `download`: the lane item JSON while `downloading`, else `null`.

**Hugging Face list.** `family` is required; `size` narrows Klein to one repository (without it both are listed); `version` (`2.3`, `2.5`) narrows LTX to the adapters of that version's repository (without it both are listed). A repository that is an adapter of several of the listed bases is listed once. `sort` is `downloads` (default), `likes`, `trending` or `newest`; `q` is at most 100 characters. A family without a base repository is a 422. The answer is `{items, next_cursor, base_models}`; pass `next_cursor` back as `cursor` for the next page, and `null` means the last page. A page can hold fewer rows than asked because gated, adult-tagged and fileless repositories are dropped. A row is `{repo, name, author, downloads, likes, files, licence, thumbnail, trending_score, created_at, updated_at, curated_id}`: `name` is the cleaned repository name, `files` counts the `.safetensors` files, `thumbnail` is a Hub URL or `null`, and `curated_id` marks a repository with a curated entry.

**Repository detail.** `GET /api/discover/hf/repo` answers `{repo, name, author, revision, downloads, likes, licence, licence_label, base_model, instance_prompt, previews, preview_videos, model_card_url, preselected, files, other_files}`. `revision` is the commit every later call pins; `base_model` is what the author declares; `instance_prompt` is the card's trigger words, comma-separated (`utils/lora_trigger.card_triggers`); `previews` are Hub resolve URLs (anything pointing elsewhere is dropped). `preselected` is the file to offer first: one marked recommended, final or best, else one without a step number, else the highest step. `files` are the choices (the preselected file and real variants) and `other_files` the training snapshots to fold. A file is `{file, size_bytes, size_label, sha256, step, marked, curated_id, save_as, renamed, state}`: `save_as` is the local name it would get (a slug of the repository name, with `-2`, `-3` when taken on disk or by a running download), `renamed` says the slug was taken, and `state` is `available`, `downloading` or `installed` (the same file from the same commit is already installed under that name). A taken name is therefore known before Use is pressed.

**Family check.** `GET /api/discover/hf/check` reads only the safetensors header of the file with two `Range` requests: the 8-byte length, then exactly that many bytes, so a header that would take the read past 2 MB is not read (the file must be one the repository lists) and answers `{status, family, size_variant, expected: {family, size_variant}}`. `status` is `match` (made for the asked model), `mismatch` (made for `family`/`size_variant`, which differ) or `unknown` (the header is unreadable, too large for the cap, or names no family).

**Download.** `POST /api/discover/download` takes `{"curated_id": "<id>"}` or `{"repo": "<owner/name>", "file": "<path>", "name": "<optional>"}` and answers `{name, status, renamed, item, trigger, trigger_source}`. A curated entry saves under its curated `name`; a repository file under `name` if given, else a slug of the repository name, numbered when taken. `status` is `queued` (a new lane item, in `item`), `running` (the same file is already downloading; `item` is that item, so two presses make one download) or `installed` (the same file is already there; `item` is `null`). `trigger` is the text to offer (the curated entry's, or the card's trigger words, comma-separated) and `trigger_source` is `curated` or `card`. Refusals come before any bytes move: 409 when a curated entry's name belongs to a different file or download, 403 for a repository file before the opt-in, 404 for an unknown id or a file the repository does not list, 422 for a bad value or a gated or adult-tagged repository, 502 or 503 when Hugging Face cannot answer.

**Progress.** The item is a lane item (`kind: "lora"`, `name` the local name, `label` `LoRA <name>`) and its progress, cancel and final states are those of `GET /api/models/downloads` and `POST /api/models/downloads/{id}/cancel`; see [Model downloads](downloads.md#model-downloads). The item adds `curated_id`, `source_repo`, `source_file`, `source_revision` and `size_bytes`. A `done` item means the file is installed and its source recorded; a `failed` one carries the reason in `message` (for example a SHA-256 mismatch) and left no file. The Models page **Import a LoRA** from Hugging Face (`POST /api/models/import-lora/hf`, body `repo_id`, optional `filename` and `name`) uses the same item and returns at once with `{status: "ok", tone, message, name, outcome, download}`; `outcome` is `queued`, `running` or `installed`, a typed `name` that is taken is a 409, and an unnamed import is saved under the file's stem, numbered when taken. It keeps the user's Hugging Face token, so a private repository they can open imports.

**Installed LoRAs.** The `loras` rows of `GET /api/workspace` and `GET /api/models` also carry `curated_id`, `title`, `trigger`, `trigger_source`, `source`, `hub`, `size_bytes` and `size_label`. `trigger_source` is `curated`, `card`, `header` or `user` (the order of trust, see [LoRA sources](app-database.md#lora-sources)) and `trigger` is the trigger words, comma-separated, or `null` when none is known; `source` is `{repo, revision, file, sha256, curated_id}` for a file the app downloaded, else `null`. `title` is the curated entry's display name, or the repository's name for a Hugging Face download, else `null`. `hub` is set for a Hugging Face download that is not a curated entry and holds what it kept: `{name, author, downloads, licence, licence_label, model_card_url, thumbnail_url}`, with `thumbnail_url` pointing at `GET /api/discover/installed-thumbnails/{name}` (null when no image was kept); it is how the Installed tab describes the file offline. `PUT /api/loras/{name}/trigger` takes `{"trigger": "<text>" | null}` and answers `{name, trigger, trigger_source, user_trigger}`; a typed trigger wins over every other source, and `null` or blank clears it. Deleting a LoRA also deletes its source row; while a generation job is running or queued the delete is refused with 409 and `detail` "Delete is off while a job runs: the job may be loading this file. Wait for all jobs to finish, then try again.".

**Memory estimate.** `POST /api/video/memory-fit` and `POST /api/extend/source` count a MiniMax H3 LoRA that is still downloading at the size its download expects (the curated entry's, or the Hub's), instead of refusing the missing file.

## Job log

`web/job_log.py` is the `jobs` component of the [app database](app-database.md): one row per finished job in `jobs_entries_v1`, ordered by `seq`. `server.py` builds it as `JobLog(app_db.app_db_path)`. `WebRunner` takes it as the `job_log` argument and writes nothing without one.

- **Which jobs.** Only image, video and upscale jobs that started (`started_at` is set) are logged. A job removed from the queue never started, and `dummy` jobs are not generation jobs, so neither is logged.
- **Once only.** A job is logged when it first reaches a terminal status (`completed_at` still unset). A later terminal event changes the in-memory status but writes no second entry, so the log keeps the first outcome.
- **Where the write happens.** `_publish_event` copies the plain facts of the job under `record.lock` and writes last, after the subscriber fan-out and the release of the claim, holding no lock. Every logged terminal is published on the worker thread, so the write never blocks the event loop; the routes of the log are plain `def` and run in the threadpool. If a future change logs queue removals, the write must move off the loop.
- **Failures never reach the job.** Building the entry and writing it share one `try/except Exception` that only emits a `UserWarning`, so the terminal event, the claim release and the next queued job do not depend on the log.
- **Partial failures.** The record counts `generation_finished` events with `status: "failed"` (`failed_runs`) and keeps the last reason. A job that still ends `completed` or `cancelled` keeps that status, and the `failed` filter of `GET /api/jobs/log` matches it through `failed_runs`.
- **Storage.** Each row holds `job_id` and the entry's JSON text as `json.dumps(entry, ensure_ascii=False, default=str)` wrote it, so a listing returns what was written (key order, `100.0`). A listing reads every row and filters and pages with `page_entries` / `matches_status`. Each operation uses its own connection, writes run in `app_db.transaction`, and there is no lock. Rows are never trimmed; they stay until `delete` or `clear` removes them.
- **Best effort.** Two `ziv ui` servers on one data directory share the table safely. A server stopped while a job runs may exit before the worker writes that job's entry. A damaged database is quarantined whole and the log restarts empty, with the old rows kept in the `.corrupt-*` file.
- **Routes.** `GET /api/jobs/log` (50 per page, newest first, `status` filter), `DELETE /api/jobs/log/{job_id}` and `DELETE /api/jobs/log` are declared before the `/api/jobs/{job_id}/...` routes. Every storage failure, and a jobs schema newer than this ziv, reaches the routes as `JobLogError` and becomes a 500 with `Could not read or write the job log: <reason>`.
- **Tests.** The autouse `_isolated_app_db` fixture points the app database, and so the job log, at a temporary directory.

## Recent prompts

`web/recent_prompts.py` is the `recent_prompts` component of the [app database](app-database.md): one row per distinct mode, format, prompt, scene and negative prompt in `recent_prompts_entries_v1`, newest by `seq`. It is separate from the job log on purpose: the log writes a job only after it started and ended, truncates the prompt, and its Delete and Clear log would otherwise remove recents.

- **What is recorded.** `_generate_from_form` calls `_remember_prompt` after `POST /api/generate` accepted a job. `recent_prompt_entry` (pure) builds `{format, prompt, scene, negative_prompt, mode, used_at}` for an inline submit: `format: "text"` with the trimmed prompt, the scene for video and the negative prompt for images, or `format: "json"` with the trimmed `json_prompt` as `prompt`. It returns nothing for `prompt_source=file`, or when the prompt (or caption) and scene are both blank. A refused submit (409, 422) never reaches it. The text recorded is the one the form sent, so the user's own text in auto-enhance mode and the Enhanced text when it is used.
- **Dedupe.** The key is `(mode, format, prompt, scene, negative_prompt)`. Recording an existing one is an `INSERT OR REPLACE` that gives the row a new highest `seq`, so it becomes the newest and takes the new `used_at`. Nothing is capped or trimmed.
- **Routes.** `GET /api/recent-prompts?mode=image|video&q=` returns `{"entries": [...]}`: the newest 50 rows of that mode whose prompt or scene contains a non-blank `q`, ignoring case. `DELETE /api/recent-prompts?mode=image|video` removes the rows of that mode and returns `{"deleted_count": n}`. `mode` is required on both and any other value is a 422.
- **Failures.** They never reach the submit: `_remember_prompt` only emits a `UserWarning`, so the response of an accepted job is unchanged. A storage failure, and a schema newer than this ziv, reaches the routes as `RecentPromptsError` and becomes a 500 with `Could not read or write the recent prompts: <reason>`.

## Video upscale jobs

`POST /api/upscale` on a gallery video queues an `upscale` job whose context, submit response and snapshot carry `media_type: "video"` (image jobs leave it out); `WebRunner.submit_video_file_upscale_job` runs it through `video_file_upscale_runner.run_video_file_upscale` after the same SeedVR2 download plan and load as the image upscale. The runner builds the result in a hidden `.ziv-tmp-upscale-*` folder beside the source, which the gallery and `/media` never list or serve, and moves it into place at the end, so a quit or a failure leaves nothing. The result embeds the source's config through `provenance.build_video_upscale_payload`, with `workflow: "upscale"` and a `source` block that follows back to the original.

## Reference images

An image job takes references on top of its start image (`image_path`). The Workspace form sends them as one repeated `reference` field, one value per row in prompt order: an uploaded file, or the text path of an image on the host. One field keeps the rows numbered as the prompt refers to them ("image 1", "image 2"), which two separate upload and path fields could not. `_resolve_reference_images` saves uploads like the start image: each is checked and named by the SHA-256 of its content (`.web_uploads/<hash>.<ext>`), and a file already there is left as it is. It also checks paths with `utils/references.py`; and `_validate_model_capabilities` refuses references for a model whose `max_reference_images` is 0 or below the count. The job's recorded settings replace `reference` with `reference_path`, the resolved files in order, which is also the name the Workspace URL and Reuse use (repeated).

A gallery image's Reuse URL names its recorded references as repeated `reference_path`, as recorded: the gallery does not check that the files exist. The Workspace keeps a row whose file is gone, marked missing, instead of dropping it, because dropping it would renumber the prompt. `image_model_defaults` carries `max_reference_images`, and the workflow contract lists the `references` controls on the image workflows only. `POST /api/references/check` takes `{"paths": [...]}` and answers `{"missing": [...]}` with the paths that are no longer files; the Workspace calls it on load, after anything that loads settings (Reuse, Load settings, a settings link) and after it deletes an image a row uses, to flag lost rows.

## Settings presets

Presets are a Web UI feature; the CLI does not know them. A preset is one YAML file, `<data dir>/presets/<mode>/<slug>.yaml` (`mode` is `image` or `video`), with the top-level keys `name`, `model` (or null) and `settings`; the folder decides the mode, so the file does not repeat it. `web/presets.py` owns the format, the slug rules and the store (writes under one lock with `write_text_atomic`).

- **Settings.** The `settings` keys are the Workspace form field names. Unknown keys are ignored when reading and writing, and missing keys count as not set. Prompt, seed, reference image and the workflow are never stored.
- **Routes.** `GET /api/presets` lists both modes sorted by name and skips invalid files. `POST /api/presets` creates one: the server derives the slug from the name and answers 409 when it is taken. `PUT /api/presets/{mode}/{slug}` overwrites (a `mode` in the body is ignored), `POST /api/presets/{mode}/{slug}/rename` renames, `DELETE /api/presets/{mode}/{slug}` removes; an unknown mode or a malformed slug in the path is 422. `POST` takes the mode in its body. Names and slugs are unique within a mode, so image and video presets can share a name.
- **Web apply.** `draft.applyPreset(ctx, preset)` (helpers in `lib/state/presets.ts`) applies a preset the same way in every workflow: keys outside the preset (prompt, seed, reference image, workflow) are untouched, and the capability gates re-run so the new model clears what it cannot use, as a manual model switch does. A model or LoRA that is not installed is skipped without a message.
- **Deselect.** A mode switch, Reset, and an extend or reuse that loads a source's settings clear the applied preset; a preset can be picked again afterwards. The applied slug is a single value in the draft (not per mode); it moves on rename and clears on delete.
- **UI parts.** `PresetMenu.svelte` is the toolbar control and, on a phone, the sheet behind the first chip; `PresetNameDialog.svelte` is the Save as and Rename dialog; `lib/state/presets.svelte.ts` is the list store.
- **Tests.** An autouse fixture in `tests/conftest.py` points the presets folder at a temporary directory, so no test reads or writes the real one.

## Model inventory

A repo-id alias can declare its image family in config via `model_alias_families` (for example `ideo: ideogram4`). The Web UI inventory and workspace bootstrap consult this declared family as an offline fast-path, so a known alias is surfaced without the network `detect_image_model` round-trip that a bare Hugging Face repo id would otherwise require. Content-based detection for arbitrary local model directories is unaffected; only aliases with a declared family skip detection.

`model_labels.<alias>.name` in `config.yaml` is how the Web UI names an alias; `utils.config.model_display_name(config, name)` returns it, or the alias itself when none is set. The server fills `label` on the workspace model options, the Models rows, download plans (and so the lane items) and `model_label` on a job's context and snapshot. The alias stays the id in every API field, CLI flag, prompt file and recorded setting; only the Workspace picker, job card, queue row and Models page show the name.

`model_labels.<alias>.download_size_label` (a `darwin` / `win32` / `linux` map, whole GB) is the one-time download size of an image alias on each platform; the workspace payload carries this platform's value as `download_size_label` on the image options. It is data entered from a dry-run download plan against an empty cache, so update it when an alias's repo or files change. The first-run dialog (`FirstRunDialog.svelte`) opens when every image model is not downloaded, no image download is queued or running and `ui.first_run_skipped` is not set. `first_run` in `config.yaml` names the models it recommends: `web/first_run.recommended_first_run_model` returns `large_model` when the machine's memory (Mac unified memory, CUDA total VRAM) is at least `min_memory_gb` within 5%, else `small_model`, and the workspace payload's `first_run` block carries that and the skip flag. `POST /api/first-run/skip` writes `ui.first_run_skipped` to the user config; it is not a writable config field.

A repo-id alias points at the upstream repo when it is ungated, otherwise at a mirror whose weight files match upstream's sha256.

Per-model Web UI capability flags — `supports_img2img`, `supports_upscale`, `supports_scheduler`, `supports_json_prompt`, `supports_first_sigma`, `dimension_min`, `dimension_max`, and `dimension_step` — are data-driven: they originate in the `model_presets` family entries, flow through `resolve_defaults`, and are emitted into the SPA's `ImageModelDefaults`. Families that do not set them inherit permissive defaults (img2img, upscale and scheduler enabled, JSON caption and first-sigma disabled, `16`/`null`/`16` dimension bounds), so gating is centralized in config rather than branching on family in the web layer.
