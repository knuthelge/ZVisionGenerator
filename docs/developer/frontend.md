# Frontend

The Web UI is a Svelte 5 app in TypeScript, in `frontend/`, built with Vite and pnpm into `zvisiongenerator/web/static/app/`. The built files are committed, so the package works without Node.

## Develop

```bash
make frontend-install   # install packages
make frontend-dev       # Vite dev server with hot reload
make frontend-test      # svelte-check and Vitest
make frontend-build     # build into the package; commit the result
```

You need Node.js 22.22.2+ (22.x), 24.15.0+ (24.x) or 26+ and pnpm 11 or newer. Run `make frontend-build` and commit the rebuilt files after every change: `make check` fails when the committed build is out of date.

| Folder | Holds |
|---|---|
| `src/app/` | The app shell, routing and `global.css` with the design tokens |
| `src/features/` | One folder per page: `workspace`, `gallery`, `prompts`, `models`, `config`, `jobLog` |
| `src/lib/components/` | Shared components, as `atoms`, `molecules` and `organisms` |
| `src/lib/state/` | Stores shared across pages |
| `src/lib/api/` | The API client |
| `src/lib/actions/` | Svelte actions for drags, holds and sheets |

Tests sit next to their source as `*.test.ts`.

## Confirmations

Ask the user to approve an action with `ConfirmDialog` (`frontend/src/lib/components/molecules/`), never `window.confirm`. It has no title: it shows the question, an optional line of information, and a cancel button plus a confirm button named after the action (danger-styled for destructive actions). Enter confirms (except on a focused button or link), Esc cancels, and a held key never confirms; while it is open, no other key reaches the page or a viewer underneath. Call `requestConfirm({ question, info, confirmLabel })`, which resolves `true` on confirm, or render `<ConfirmDialog>` directly when the dialog needs a body or stays open while the action runs (`pending`). A `parts` list (`{ label, size, lines }`, one block per item, shown between the question and the information) is for a question about several things; `infoTone: 'warning'` colours the information line.

**Download questions.** Every action that would download a model asks through `confirmDownloads(plan)` (`lib/state/confirmDownloads.ts`), which resolves `true` at once for a plan with no parts and otherwise shows one dialog with a block per part, its size, its licence lines and the free space (**Download anyway** when it is short or the plan is `unchecked`). A job plan comes from `planGenerate` or `planUpscale`; a Models-page row's plan becomes a one-part job plan with `jobPlanOfRow`. The Workspace submit, `startUpscale`, the Enhance button and `downloadStore.request` all call it, so a new action that downloads adds its plan request and this one call.

Let the user choose a path on the server's machine with `PathField`, or `PathInput` (a path box with completion) and `PathBrowser` (the browse dialog) where a field needs its own layout. Each takes a browse purpose; the purposes, with their folder or file kind and accepted extensions, live in `web/path_browser.py`, so add one there for a new kind of path.

## Licence marks

`LicenceMark` (`lib/components/molecules/`) shows the terms of a model from its `licences` (the records the server sends with every model option, Models-page row and plan; the background removal models' own are `matte_licences` on the workspace payload). It renders nothing for an empty list. Without a `label` it is a muted `ⓘ` button; with one, such as `Non-commercial`, a neutral badge button. Hovering opens a card with each record's name, supplier, summary, credit line and links, and a click, tap, Enter or Space pins it. The card is moved to `<body>` by the `popover` action because the Models tables clip. Put the mark beside a control, never inside a button.

## Audio in the Web UI

`AudioPlayer` (`lib/components/molecules/`) shows a take as a seekable waveform over the browser's own `<audio controls>`, which is the only set of controls, so keys and screen readers use the native element. A gallery listing sends `peaks: null`; `audioPeaks.ensure(asset)` (`lib/state/audioPeaks.svelte.ts`) fetches `GET /api/gallery-peaks` once per asset for the tiles, the stage and the viewer's shown take. A sideways drag on the waveform seeks and never pages the stage or the viewer (`data-own-drag`, read by `OWN_DRAG` in `actions/pan.ts`). A take never autoplays, and the element is paused whenever its `src` changes or the player leaves. The pure helpers (length labels, the cut note, the viewer facts) are in `lib/state/audioAsset.ts`.

- **Stage.** `AssetTile` in the `stage` density renders the player instead of an image; a take that reached its model's cap (`asset.cut`) adds a "Cut at" `Badge`. Several takes of one job are players in a column.
- **Tile.** A grid tile shows the kind icon, the first lines of the words, a small waveform and the length. A file without this app's settings shows a bare layout. No tile plays.
- **Viewer.** The player, the words in labelled blocks, then Generation and File facts. `upscale` and `extend` are `null` on a take, so the bar offers neither.
- **Job card.** A job with `media_type: "audio"` counts takes and shows `AudioAurora` in its preview slot, a canvas of ribbons that follows the stage of the take (`auroraStage`, from the latest `audio_progress`) and collapses onto the waveform when the take is ready. Its phases come from `audio_progress` events kept as `job.audio`: `audioRows` in `jobView.ts` gives a song one row per phase and speech and sound one row. The header bar follows `audioFraction`, so it only moves forward. With `prefers-reduced-motion` the canvas redraws on each event only.
- **Models page.** An Audio models panel follows Video models, shown only when the inventory lists `audio_models`. Downloads go through `downloadStore` with kind `audio`. An audio model's memory fit is the GPU's alone, so `ModelStatusBadges` words an estimate without `system_gb` as GPU memory only.

**The Audio tab.** The kind alone decides what the tab offers (Lyrics for Music, Length for Sound, Voice for Speech); `AUDIO_KINDS` in `lib/types` is the one list of kinds. The tab opens on the kind it was left on (`draft.audioKind`) and takes the model last chosen for each kind (`draft.audioModels`). `lib/state/audioDraft.ts` holds the pure parts, `lib/state/musicMode.ts` mirrors the song-or-instrumental rule of `music_mode` (tested against `tests/audio/music_mode_cases.json` with the Python rule), and `features/workspace/audioView.ts` derives what the open kind sends and the one reason Generate is off, which `buildFormData`, the Settings footer, the phone composer and the chips all read.

- **Toolbar and compose.** The Kind control comes first, then the model `Select`, its `LicenceMark` and the memory badge; presets, Quantize and LoRAs are not rendered. `AudioCompose.svelte` replaces the prompt boxes, and its tools row holds Recent prompts only, one list per kind.
- **Settings.** `VoiceSection` comes first for Speech, then Batch, Length (s) for Sound and Seed. On a phone the chips are built by `audioChips`.
- **What a Generate sends.** `audioFormData` builds the fields Copy CLI reads for the open kind only (see [Web server](web-server.md#audio-jobs)). A setting (Lyrics, Tempo, Key, length, Sound Type, Delivery) goes only when its control is shown for the open (model, kind): `workspaceCapabilities` lists the workflow's controls minus the `hidden_controls` of the model's row, and `AudioView.shown` carries the result. Delivery also needs a built-in voice. A blank `tempo`, `key` or `seconds` is Auto. The plan, the download dialog and the submit all read this one form.
- **Settings in the draft.** `audioTempo`, `audioKey`, `musicSeconds` (0 is the model's default), `soundType` and `speechDelivery` sit in the `audioSettings` and `audioDelivery` scopes, so a Reset puts them all back to Auto and the defaults. An exact prefill (Reuse, Retry, Load settings) does so only for the settings of the kind it opens (`AUDIO_KIND_SETTINGS` in `audioDraft.ts`) before it sets the take's own, and leaves the other kinds' settings as the form has them. `audioPrefill` reads the flat keys of a Reuse link (`tempo`, `key`, `seconds` by kind, `sound_type`, the five delivery keys), and `audioCliCommand` writes them as flags, leaving out Auto and default values. The `audio_settings_cases.json` and `audio_cli_cases.json` fixtures pin both round trips in Vitest and pytest.
- **The speaker's consent.** The tick lives in `lib/state/voiceConsent.svelte.ts`: in memory only, never in the draft, an address or a job's settings. A new recording, Reset and a prefill that replaces the voice clear it. A Use as → Voice from a take made in a built-in voice (no `voice_clone`) marks the voice `exempt`, so no tick is asked for.
- **Held uploads.** The recording is held in `heldUploads.voice` and persisted in the upload store, so it survives a visit to the Gallery and a reload, like the Video tab's audio track.

**Use as for takes.** For an audio take the asset menu and the viewer's Use as list **Audio track** and, for a speech take, **Voice** (disabled with the reason when the Video model cannot follow a track, or the take is over the speech model's `max_voice_seconds`). Both go through the prefill a Reuse uses with `use_as` set, so only that one slot changes. The params are the contract the Audio tab reads:

| Target | Params |
|---|---|
| Audio track | `workflow=txt2vid`, `audio_track_path` (the take's file), `audio_track_start=0`, `use_as=audio_track`; the draft's other slots, its first frame included, are kept and only the Video tab's held upload goes |
| Voice | `workflow=speech`, `voice_path` (the take's file), `voice_text` (the take's text), `use_as=voice`, and `voice_clone=true` only when the take was made from a recording (`has_reference_voice`) |

`voice_clone` tells the Speech tab to show the consent tick: a voice that is itself a clone is a person's, while a take the model chose the voice of (*Any*) needs none. The server decides the same way when the job is submitted (`voice_needs_consent`). The speaker's consent is never in a URL or a draft.

## Toasts

Report the outcome of an action with `addToast(message, type, options)` from `$lib/state/toasts.svelte`. One toast shows at a time at the bottom centre of the page content (pages with a fixed left sidebar set `--toast-inset-left`); the rest wait their turn, shown as "+N". A repeat of a waiting or showing message merges into it ("×2"), and an error goes ahead of every non-error. Each tone has a default time on screen (success 2.5 s, info 4 s, warning 7 s); errors stay until dismissed, or give way after 8 s once other toasts are waiting, and hovering or focusing a toast pauses it. Pass `{ action: { label, run } }` for one follow-up such as Retry, and `{ timeout }` only when the default doesn't fit. An action that acts on a page must not outlive it: keep the id `addToast` returns and call `dismissToast(id)` in the page's `onDestroy`. The exception is the download lane (`lib/state/downloads.svelte.ts`): its store raises the done and failed toasts, and their Retry runs the store's request flow rather than page code, so they stay after the page that began the download is gone. Raise one toast per action, and skip it when the screen already shows the result.

## Requests and errors

Send requests through `api` in `$lib/api/client`, which throws `ApiError` with the HTTP `status` and the server's `detail`. Show a failed request with `errorText(err, fallback)`, never `err.message`, which holds the method, path and raw body. Offer Retry only when `isRetryable(err)`: a 4xx means the server refused the input, and the same request fails the same way again.

## Design system

The Web UI has one design system. Its tokens live in `@theme` in `frontend/src/app/global.css`, and its component classes are the `ui-*` classes in the same file. Build pages from the shared components in `frontend/src/lib/components/` (`Button`, `Input`, `Select`, `Toggle`, `Badge`, `Panel`, `Segmented`, `ActionBar`, `PageHeader`, `KeyValueList`, `Alert`, `EmptyState`, `InspectorSection`, `InspectorRow`) or, where no component fits, the `ui-*` classes (for example `ui-chip`), rather than styling elements by hand.

- **Size:** controls are 28px (`h-control`), small ones 22px, rows 30px. Buttons that sit together share one height; inside an `ActionBar` every button is 36px and the one marked `main` takes the remaining width.
- **Type:** four sizes: `text-meta` (11px), `text-ui` (12px), `text-content` (13px), `text-title` (16px), plus `text-display` (30px, 24px on compact screens) for the first-run welcome headline and the recommended model's name only. Nunito (`font-heading`) is for titles, area names and the main action; monospace is for numbers, paths and shortcuts.
- **Labels:** field and row labels are sentence case (`ui-label`). The one small-caps style (`ui-area-label`) names areas: panels, sections, table headers and menu groups.
- **Shape and surfaces:** corners are 4px for chips and badges, 6px for controls and 10px for containers. Overlays (menus, popovers, tooltips, toasts, dialogs) use `bg-overlay`, darker than any page surface, with a faint ring and never a drop shadow; `bg-raised` is for section header bands and `bg-fill` for the prompt box.
- **No borders:** containers are separated by shade, and buttons, fields, chips and badges are filled shapes. Dividers between rows and sections stay. Draw an outline only where it means something: focus, a field with an error, the selected tile, and the dashed edge of drop zones and add buttons. Segmented controls are a recessed well with the chosen option as a lighter pill.
- **Main action:** each section (a bar, panel, form, dialog or popover) has at most one main action, a `primary` button: teal fill and a bold Nunito label. Every other button in the section is secondary.
- **Reference pages:** Config and Models centre their content at `max-w-page` (1200px), with the page bar lined up to it. Settings use label-left rows (`FormField layout="row"`), and tables use `ui-table-comfortable`.
- **Colour:** neutrals are Graphite greys with no tint. Teal means on, selected or the main action; coral (`accent-coral`, Blob's beret) marks `$snippets` and amber `{a|b}` choices; red is for errors and destructive actions, which always show red text. Info messages stay teal, never coral. Text is at least 4.5:1 on every surface. Use tokens, never raw palette classes or colour literals; `make check` fails on them.
- **Focus:** every control shows the same 2px teal outline with a 2px offset.
- **Touch is a layer, not a breakpoint:** `@media (pointer: coarse)` in `global.css` raises the size tokens (controls 40px, small controls 32px, rows and action bars 44px, the switch 40 × 24) at every width, so an iPad in the desktop layout gets finger-sized targets and a mouse keeps the desktop density. Build sizes on the tokens, never on literal pixels, so they follow. Numbers get − and + steppers (`InspectorNumber`, press and hold to repeat) because a label cannot be scrubbed when a drag scrolls; `InspectorRow` skips scrubbing on a coarse pointer. The `layout` store (`lib/state/layoutMode.svelte.ts`) tells components the composition (`compact | tall | wide`) and whether the pointer is coarse.
- **Hover only where there is hover:** a touch screen keeps `:hover` on whatever was tapped last, so every `:hover` rule sits inside `@media (hover: hover)` (`make frontend-hover-check`, part of `make check`, fails on a bare one; Tailwind's `hover:` variant already does this). A finger gets an `:active` pressed state under `@media (hover: none)` instead, and anything a mouse reveals on hover is always shown under `(hover: none)`. On a phone, fields are at least 16px so focusing one does not zoom the page, and the page never scrolls or bounces (`overscroll-behavior: none` on `html` and `body`).
- **The visible viewport:** `lib/state/viewport.ts` (started in `main.ts`) sets `--app-height` and `--app-top` from `window.visualViewport`, and puts a page the browser scrolled back at the top when no field is being edited. The app root and every full-screen layer use `.ui-viewport`, which is fixed to those values, so they sit above an on-screen keyboard (iOS ignores `interactive-widget`) and follow Safari's toolbar at once. Build full-screen layers on `.ui-viewport`, never on `inset: 0` or `100vh`.
- **Three compositions of one Workspace:** the same panes (`ComposePane`, `SettingsPane`, the toolbar, the stage, `GalleryStrip`) are arranged by `layout.mode`. *Wide* (1024px and up) is the sidebar beside the stage. *Tall* (640 to 1023px, a portrait tablet) puts the stage and strip over Compose and Settings side by side. *Compact* (under 640px, or under 500px tall) makes the stage the screen: a `TopStrip` and `NavDrawer` replace `TopNav`; a `SettingsStrip` of chips (`settingsChips.ts`) opens one `SettingPopover` at a time, All opens `SettingsPane` in a `Sheet`, and a composer at the foot hosts `ComposePane` folded or open. Everything stays inside the Workspace form, so every field submits in every composition. A running job shows `JobPreview` large with `JobCard` beside it on wide and tall and `JobBar` over it on compact; `ActionMenu` and `Modal` render as a `Sheet` on compact. Nothing is hidden behind a phone pattern on a wide screen.
- **Stable frames:** nothing moves under a finger while a page loads. *The frame first:* a page draws its complete frame synchronously from its composition (bars, strips, panels, the grid, action rows) and requests only fill it; a loading state lives inside the slot it is loading (placeholder chips in `SettingsStrip`, the disabled actions of `AdminPageShell`, the Gallery's placeholder tiles) and never changes the height of anything around it. *Pages remember:* a page component is rebuilt on every visit, so what it loaded lives in `lib/state/pageMemory.ts` (the Workspace context, the Gallery view with its scroll position, the inventory, the config); the page adopts the remembered value on mount, draws it at once, then asks the server again and replaces it. *Anchors do not move:* the top strip, the composer, the settings strip and page bars keep their place and size; content that changes size changes inside a box reserved from the start. A new page follows all three, and page switches stay a hard cut, which is what a native tab switch does.
- **One Gallery:** the strip on the Workspace, the stage's stepping through earlier outputs, the Gallery page and the viewer all read `lib/state/gallery.svelte.ts`, which keeps one list per query (`filter` and `sort`). The default query is the strip's and the stage's and the store loads it; the Gallery page loads its own query's pages and commits them with `setView`, so `removeAssets` and `mergeOutputs` reach every list, a visit comes back where it was, and the page's first visit shows the strip's list. There is no history route or store; `/api/gallery` serves both.
- **One viewer, native on each device:** `molecules/AssetViewer.svelte` is a panel over the page on wide and tall layouts (a backdrop that closes on click, the details column beside the image) and the whole screen on compact. It follows the open asset by id (`currentId`), never by place, so new outputs or a delete elsewhere never move the view. It takes the tile that opened it (`origin`) and flies a copy of the thumbnail between the tile's box and the image's box on open and close (`viewerFlight.ts`, a FLIP on the transform), with the thumbnail standing in until the image has loaded. On touch, a track of three panes follows a sideways drag and settles to the neighbour before the index changes (`viewerPager.ts` decides from offset and velocity); a pull down shrinks the image and clears the backdrop (`--pull`), and lets go into the tile through the same flight; a pull up opens the details as a half sheet in flow under the image; one tap hides the chrome. A hold on the image (`actions/hold.ts`, which swallows the click the lifting finger makes wherever it lands) or a right-click on a tile or the image opens the asset menu, anchored at the pointer through a 1px anchor. The viewer is an escape layer, so Escape closes it, the shortcut list first.
- **One sheet, and drags that follow the finger:** every sheet on a phone is `molecules/Sheet.svelte` (the Job and All settings sheets, the enhancer, menus, dialogs): it slides in and out, is as tall as its content up to the screen under the top strip, and pulls down to close through `actions/sheetDrag.ts`. The grab bar and head carry `data-sheet-handle` and always pull; the body pulls once its content is at the top. The `SettingPopover` and the viewer's details use the same action. Drags are built on `actions/pan.ts`, which decides on the first movement whether a touch is the surface's (and then cancels every move, so the browser cannot start scrolling under it) or the page's; deciding later loses to native scrolling on iOS and Chrome. Its pure helpers (`lockAxis`, `releaseVelocity` from the last 80 ms, `rubberBand`, `canScrollToward`) carry the decisions and are unit-tested. A press and hold is `actions/hold.ts` (fingers and pens only; it marks the node `data-holding` with `--hold-ms` while held, so `.ui-holdable` fills a bar along its foot, and swallows the click and the browser's long-press menu once it fires; only the first finger down holds, and a second finger anywhere on the page cancels the hold, so a pinch never opens a menu): Generate's new-seed menu, the asset menu on every `AssetTile` and the viewer's stage use it. The `NavDrawer` swipes closed on the same tracker, and the Workspace stage uses it to follow the finger sideways through history and up to the Gallery (`features/workspace/stageSwipe.ts` decides the outcome, and a trackpad's sideways wheel steps once per gesture). The Prompts page arranges sets, entries and snippets with pointer events, not HTML drag and drop (which never fires for a finger): `reorderDrag` in `features/prompts/dragDrop.svelte.ts` starts at once from a grip for a finger and after a few pixels for a mouse, and `dropTargetAt` reads the drop zones from `data-dnd-entry`, `data-dnd-set` and `data-dnd-snippet` under the pointer.
- **Workspace tabs and image slots:** the top bar has three tabs, `image`, `video` and `audio` (`NavTab`, `navTab(workflow)` in `lib/state/workspaceTab.ts`); `visibleTabs` shows Audio when the contract lists an audio workflow. Extend is a kind of Video, chosen with the Kind control and offered when the contract lists `extend`; `draft.state.videoKind` remembers the kind Video was left on, as `audioKind` does for Audio. `workspaceTab(workflow)` is the slot a workflow keeps its images and audio track in, and gives `extend` a slot of its own. `draft.state.workflow` is derived from the tab and its start image (`img2img` or `img2vid` when the start image is set and the model takes one, otherwise `txt2img` or `txt2vid`); on the Audio tab it is the open kind. The prompt text is kept per tab: Image and Video each hold their own, and Video's two kinds share one. Uploads persist in IndexedDB (`lib/state/uploadStore.ts`, `lib/state/heldUploads.svelte.ts`), and Generate waits until `heldUploads.restored`. What a model takes for images is answered once, by `imageSupport` (`lib/state/imageSlots.ts`).
- **One scope table:** every field of `DraftState` has exactly one owner in `FIELD_SCOPE` (`lib/state/resetScope.ts`); a field added without a scope fails `svelte-check`. A transition is a list of scopes: `RESET_SCOPE` holds the one of each tab, and `draft.resetSelections` takes the values `defaultsFor(ctx, state, extendSource)` resolves for those scopes and leaves every other field as it was. `REUSE_SCOPE` is the same per tab plus the text, the model and, on Extend, the source: `loadFromUrl(..., { exact: true })` puts those scopes at `defaultsFor` before it sets the params. Only a Reuse and a Load settings are exact (`reuse=true`); a Use as (`use_as`), a deep link and a preset apply only what they name. A scope that holds uploads also forgets them. Anything a new field needs beyond that goes into `defaultsFor`, not into a keep list.
- **One settings table:** `SETTING_ROWS` (`features/workspace/settingRows.ts`) lists the Settings pane's rows with their draft keys, the phone chip they belong to and when they show. The changed dots, the Reset badge, the chips' `changed` flags and each popover's Reset all read it; a test compares it to the setting scopes. Image and Video each keep their own text, settings, model with its LoRAs and quantization, and preset: opening the other mode saves the open mode's `settings`, `model` and `preset` scopes under `savedSettings` (and its text under `savedText`) and brings back what the entered mode saved (`_withModeOf` in `draft.svelte.ts`). The Audio tab saves the mode it leaves and changes nothing else, and leaves LoRAs out by swapping the family's LoRAs on entry and exit (`_swapFamilyLoras`).
- **One image view:** `imagesView` (`features/workspace/imagesView.ts`) derives from the draft, the model's capabilities and the held uploads which images the open tab uses. `WorkspacePage` computes it once and passes it down, so what is shown, Generate's gating (`block`) and what `buildFormData` sends (`sent`) always agree. References are rows numbered by position. A row whose file is gone stays, so the prompt's "image 2" keeps its meaning, and blocks Generate. The Workspace flags missing paths with `POST /api/references/check`.
- **One audio track view:** `audioTrackView` (`features/workspace/audioTrackView.ts`) does the same for the Audio track of Video and its Extend kind: each slot keeps its own `audioTrack…` or `extendAudioTrack…` draft fields and held file, and the view says whether the track is in effect (set, on a model with the capability), what `buildFormData` sends and whether a lost upload blocks Generate. While a track is in effect `workspaceCapabilities` turns `showAudio` off, so the Audio switch, the enhancer's Sound options and the `audio` field all go, and turns the Upscale controls off on a model that cannot upscale a clip made from a track.

## Discover LoRAs

The drawer lives in `features/workspace/discover/`: a side `Modal` (a `Sheet` on a phone) mounted by `WorkspacePage`, so it shares the page's draft and download state. `discoverView.ts` holds its pure logic (the target model, a LoRA's status, filters, tiles, details and the footer); requests go through `lib/api/discover.ts`. The Models page opens it with the hash `#/workspace?discover=loras`.

- **Downloads.** A LoRA download is a lane item of kind `lora` in `downloadStore`. `lib/state/loraDownloads.ts` turns the lane into what a chip shows and what holds Generate back; a failure wins over a download still on its way. Removing a chip never stops a download. A failed item stays in the store after the server stops listing it, until it is retried or its LoRA deleted, so a red chip doesn't turn ready by itself.
- **Trigger words.** `features/workspace/triggerMenu.ts` builds the Triggers menu from the text Generate sends and inserts a chosen word at its start; nothing is written into a prompt without a choice.
- **Toasts on a phone.** `actions/dockHeight.ts` publishes the height of the phone's controls as `--toast-dock`, so a toast never covers them.

## The mascot

Blob is one SVG, `atoms/Mascot.svelte`, with a `mood` (13), a `tool` (`brush` or `clapper`), a `size` and an optional `progress` (0 to 1) for the creating canvas. Every mood is CSS on the same parts, and a mood change blends from the pose on screen (`blendInto`), so an idle mascot costs no script. Below 48 px he is drawn in a simpler form (`data-simple`: bead eyes, no hands, tool, brows or effects), which is also what `public/ziv-icon.svg` shows.

- **Effects.** The creating canvas (`mascotArt.ts`) is drawn at the step the job's progress gives (`tileStep`; the last step comes at `FINISHING_FRACTION`, where the mood turns to finishing). While no progress is passed (between the items of a batch, in the stages around generating) it holds its last step. `WorkspacePage` passes `mascotProgress(job)` to the spots on a job. The mood effects (the thought bubble, the pixel Zs, the creating and finishing canvas, the confetti) are always mounted and shown by their mood's opacity rule, so the pose blend fades them in and out with everything else. Each has a still frame under `prefers-reduced-motion`.
- **Spots.** `MascotSpot` wraps him for a place on a page and passes `progress` through; spots that share a `travelKey` hand him over. `mascotFlight.ts` holds the transitions: a spot with no previous spot is sampled in (Denoise in, 800 ms), a spot that follows another receives him as a stream of 16 x 16 pixels along an arc above the page (Latent stream, up to 1 s). A spot that no other spot takes over simply disappears. Call `rememberMascotSpots()` before a change that swaps spots, so the stream starts where he was.
- **Canvas only in transitions.** `mascotCanvas.ts` bakes the SVG with each part's current pose, rasterises it once (a hand-off bakes the old spot's pose as he leaves and rasterises it only if a spot takes him over) and draws the effect on a canvas fixed on the `--z-mascot-effect` layer (over the page, under the viewer, sheets, dialogs and toasts; over the dialog or sheet his spot sits in), sized to the area the effect covers (his box, or both spots and the arc between them for a stream) and removed at the end. The spot is hidden until the effect hands over. Where the browser can animate but has no canvas a spot pops in with a short scale-up; where it cannot animate, and under reduced motion, he is simply there, with no transition.
- **The logo.** `MascotHome` draws him at 1.39 times the logo's size, offset so his body lines up with the static icon; his dashed outline uses the same silhouette.
