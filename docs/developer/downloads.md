# Model downloads

A model that is not on disk is fetched before it loads, as a step of its own, so the Web UI can show bytes, speed and time left and offer Stop. The pieces are plain functions and small value objects in `downloads/`, composed by `ensure_downloaded`:

1. **Plan.** A planner returns `DownloadTarget` values (repo, revision, allow and ignore patterns, optional `local_dir`) for the files the load will read: `downloads/plans.py` composes the platform planners with the sources of the models built on first use (`built_model_plan`) and the SeedVR2 tier files (`image_plan`, `video_plan`, `seedvr2_plan`, `enhancer_plan`, `matte_plan`). A plan is `()` when nothing is to be fetched (a local folder, a built Instant folder, a folder the app did not build, which the build refuses) and `None` when it cannot be made now (offline with no cached file index); callers skip the ensure step for `None`. Planners mirror the patterns of the code that will load the model (mflux's weight definitions, mlx-lm's `DEFAULT_ALLOW_PATTERNS`, diffusers' pipeline files) so the downloaded files are exactly the loader's.
2. **Presence.** `target_present_offline` decides without the network whether a target is fully on disk (cached files, complete weights, or a complete `local_dir`). A present part is skipped.
3. **Dry-run.** `check_target` calls `snapshot_download(..., dry_run=True)` and returns the files and bytes still missing. It returns `None` when the Hub cannot be reached (offline mode, no connection, timeout), and raises `RuntimeError` when the Hub refuses (gated or missing repo or revision, server error). A gated or unauthorized refusal is one line from `downloads/hub_access.py` (`refusal_message`): the repo's Hub link plus `hf auth login` when `token_source()` finds no token; the worker, the CUDA image planner (`RuntimeError` instead of `LookupError`), job failures and both CLIs use the same `describe_refusal`, and any other error keeps its own text. `dry_run` needs the network: offline, the part is **unchecked** and the load proceeds as before, with the loader's own text phases.
4. **Child.** `run_in_child` runs `python -m zvisiongenerator.downloads.worker '<target json>'` unbuffered, in its own session (Windows: a new process group) so a terminal Ctrl+C does not reach it. The worker calls `snapshot_download` with a `tqdm_class` sink that counts the two aggregate byte bars ("Downloading bytes" as wire, "Reconstructing" as written; they overlap and are never summed) and prints `ZIV-DOWNLOAD {json}` lines on stdout every 0.5 s while the counts change, then a `done` or `error` line. The parent drains the lines on a reader thread, polls `cancelled()` and the exit code, and treats a missing `done` line as failure. The wire bytes of a xet transfer are a little below the file bytes (deduplication and compression), so a part's last report snaps to 100%. The child exits when its stdin closes, so a hard server kill leaves no orphan.
5. **Flights.** `DownloadFlights` keeps one flight per destination (`DownloadTarget.key`: repo, revision and local folder, plus the files wanted when the target downloads into a plain folder, so two files of one repo in one folder are two flights). The first caller owns the download; others wait and mirror its progress with `shared: true`. When a flight ends stopped or unchecked, a waiter re-checks its own target and claims it, so a stale result is never read. Finished files stay, so the re-claimer downloads only the rest.
6. **Ensure.** `ensure_downloaded(targets, flights=, report=, cancelled=)` walks the parts in order and returns `READY`, `UNCHECKED` (a part could not be checked; the rest is skipped and the load proceeds as before), `STOPPED` (this caller owned a download and stopped it) or `DETACHED` (this caller stopped waiting for someone else's download). It raises `RuntimeError` for a refused dry-run or a failed download, naming the repo and the bytes fetched. Reports are throttled to one per second, except a part's first and an owned part's final one. Every collaborator (`present`, `check`, `run`, `clock`) is a parameter.

**Job parts.** `web/job_downloads.py` plans what one Web UI job downloads as `JobDownloadPart` values (`label`, `event_model`, `model_id`, `role`, `targets`): the generation or upscale model (`role` `model`), the prompt enhancer (`enhancer`), the background removal models (`matte`) and a SeedVR2 tier. `event_model` is the `model` value of the job's `model_downloading` events and `targets` is `None` for a part that cannot be checked now. `label` and `event_model` are the same display name: `model_display_name` for an image or video model, the SeedVR2 tier label ("SeedVR2 7B q8") and "Smart enhancer model" for an enhancer tier (the enhancer's `repo[@revision]` when no tier names it). `model_id` is the key of the part's licence records: the alias, `matte`, `seedvr2` for every SeedVR2 tier, and `enhancer-fast` or `enhancer-smart` for an enhancer tier (a custom enhancer model has none). `WebRunner` takes the targets, role and event name of every download step from the part builders (`image_model_part`, `video_model_part`, `upscale_model_part`, `seedvr2_part`, `seedvr2_tier_part`, `matte_part`, `enhancer_part`), the Models page builds its rows with the same ones (`model_download_plan.row_plan`), and `job_download_parts` lists all parts of a job from its request, which is what a plan route shows. An enhancer that is missing while Hugging Face is offline is an unchecked part there; a running job still fails in preflight with the `RuntimeError`. The builders call the planner functions directly; tests replace them on `web.job_downloads`.

**Job plans.** `POST /api/generate/plan` (the form `/api/generate` takes; unknown `mode` is 422) and `POST /api/upscale/plan` (the body `/api/upscale` takes) tell the Web UI what a job would download before it is queued. They run the submit route's parse half (`_parse_image_job`, `_parse_video_job`, `_parse_audio_job`, `_parse_upscale_body`, which the submit then queues), so the plan and the job cannot disagree. The generate plan is made from the fields alone: the uploads in the form are stand-ins that are neither read nor saved (see "Plan without files" in [Web server](web-server.md)), so a file goes up once, with the submit. `job_download_parts` lists the parts in the order the runner fetches them (enhancer, model, background removal), `drop_in_flight` removes the targets a running flight (`DownloadFlights.active()`) already fetches, and `parts_summary` sizes the rest with the Models page's dry-run and space estimate, without a Hub call for a part that is on disk. It returns `{parts: [{label, model, bytes}], total_bytes, space, unchecked, licences}`: `unchecked` is true when a part cannot be planned or the Hub cannot be reached (that part is listed with `bytes: null`), and an enhancer that is not configured is a 422 with the configuration's message. A refusal by the Hub is a 424. Not covered: LoRA downloads and imports, checkpoint conversion, Repeat and Next, jobs already queued, and clients of the CLI and the API.

**Audio.** `audio_plan(preset, platform_key)` turns the files of a preset's platform entry (`audio_model_presets.<model>.platforms.<cuda|mps>.files`) into one pinned target per repository; it reads the config alone, so it never returns `None`. `job_download_parts` returns one `model` part for an `AudioGenerationRequest` (`audio_model_part`), labelled with the preset's label and planned for `backends.audio_platform_key()`. A preset lists its repositories at full 40-character commits, with file names or patterns for each, so a plan is the same for every user. `audio_cli` prints the licence line before the first download of a restricted model, as the other CLIs do.

**Background removal.** `matte_plan()` returns the two pinned targets of `utils/matte_models.py` (BiRefNet, then ViTMatte), or `None` offline. A transparent web job downloads them before its model loads (`WebRunner._ensure_matte_downloads`, events with `role: "matte"`); `ziv-image` does so in `image_cli`. The Models page shows one row for both (`kind` `matte`, name `background-removal`), removed with `DELETE /api/background-removal`.

**MiniMax H3 plans.** `backends/__init__.h3_download_plan` dispatches by platform, and `downloads/plans.py` routes the `h3` family to it (`utils.config.video_companion_repos` lists the repositories downloaded beside the main one, for the Models page and for deleting). Windows and Linux (`cuda/download_plan.h3_download_plan`) list the main repository at its pinned revision with `repo_allow` and `repo_ignore` patterns (the parts the app never loads are left out), the first four shards of the NF4 text encoder, the turbo LoRA file, and with `upscale` the latent upscaler's file (0.69 GB, from its own repository at a pinned revision, which `video_companion_repos` lists with the other companions). macOS (`mac/download_plan.h3_mlx_download_plan`) lists the INT8 transformer's files (unless `-m` is a local folder that carries its own transformer), the `FL2VA` components (tokenizer, processor, both VAEs and text-encoder shards 1-11 and 14) and the turbo LoRA (not for a converted folder, which holds its turbo merge), every file literally, so the presence check cannot pass on an empty or partial folder. Each platform then builds a stored copy from the download on first use: `<name>@q4` (CUDA; `stored_copy.copy_name` names it after the model it was picked by, so the stock `h3` keeps `h3@q4` and a fine-tune has its own) and `h3@mlx-te4` (the macOS text encoder); deleting the model removes its own copy with it.

**Local H3 folders on macOS.** `h3_video.local_int8_transformer` decides what a local `-m` folder contributes, and `resolve_mlx_files` and `h3_mlx_download_plan` both follow it through `local_transformer_dirs`, so the plan and the loader agree. It looks in `FL2VA/transformer` and then `transformer/`. A folder in the port's INT8 layout (`config.json`, `quant_config.json`, `model.safetensors.index.json` and every shard it names) is loaded as is and its plan has no transformer target; an INT8 folder missing its index or a shard raises `FileNotFoundError`. A folder with no transformer weights falls back to the preset's pinned INT8 transformer, as a Hub reference does. A folder with any other transformer (the official bf16 release or a fine-tune of it) raises `ValueError`, because the stock transformer must not stand in for it; `ziv convert --model-type h3` turns such a checkpoint into a converted folder (`ziv-h3.json`), which `resolve_mlx_files` loads with stock's components and no turbo LoRA, as its turbo is merged.

**Stored-copy sources.** `utils.stored_quant.file_identities` records each source file's identity in a copy's manifest (`ziv-quant.json`), and a copy whose manifest differs from the current sources is rebuilt. A resolved Hugging Face cache blob is named by its content hash, so its name and size are enough. Any other file, such as one in a local model folder, also records `mtime_ns` and `inode`, since a replaced file can keep its name and size; hashing tens of gigabytes was rejected. A copy built from local files therefore rebuilds when the file is replaced or moved. Copies built from Hub downloads keep their manifests unchanged. `utils.quantized_weights.decoded_tensors` multiplies scaled FP8 inputs by their scales instead of casting them, which only matters for local FP8 fine-tunes; it also decodes ComfyUI's INT8, ConvRot, W4A4, W4A8, W6A8, NVFP4 and MXFP8 weights for the video converters.

**Stop and detach.** Stopping an owning job or lane item terminates the child (killing it after `grace_secs`) and deletes its `*.incomplete` files; finished files are kept and resume is per file, so the file in progress starts over. A job that only waits on another download is detached instead: the job ends and the download continues. Stop has to end the process: raising from the tqdm sink does not stop hf_xet's transfer, and an xet download does not grow its `*.incomplete` file as it goes, so there is nothing to poll in the cache either; progress comes only from the sink.

**Memory.** The child's memory is bounded by hf_xet's download buffer, which it sizes from host RAM (about RAM/16 plus RAM/64 per file in flight), not by file size, so a multi-GB file does not need that much memory. `child_env()` sets `HF_XET_RECONSTRUCTION_DOWNLOAD_BUFFER_SIZE=512mb` unless the parent environment already sets it, which about halves the peak at the same speed, so a download can run beside a generation.

**Event contract.** Web jobs publish `model_downloading` with `mode` (`image`, `video` or `audio`), `role` (`model`, `enhancer` or `matte`), `model` (label), `repo`, `part` and `parts` (1-based, this job's plan), `bytes_done`, `bytes_total` (null if unknown), `bytes_per_sec` and `download_eta_secs` (null until known) and `shared`. It is published at most once a second per job plus each owned part's final report, and replaces the previous `model_downloading` in `record.history` so a client that connects later replays only the latest one. A job stopped during a download ends with `job_cancelled` carrying `download: "stopped"` or `"detached"`. The on-demand Enhance button's own NDJSON download frames are separate and unchanged. The Svelte job card turns the event into a row inside the load step (the enhancer's into the Enhance step), and ends it at `model_loading` (the enhancer's at its loading or rewriting events).

**Models page.** `web/model_download_plan.py` plans a row (`row_plan`; the kinds are `model`, `audio`, `enhancer` and `matte`, and an `audio` row is an audio model by its id, planned from its preset's pinned files), judges offline whether it needs a download (`row_download_needed`, used by the workspace payload for the Download button), and returns the row as one `JobDownloadPart`, so `parts_summary` sizes it as it sizes a job's parts. `DownloadLane` (`web/download_lane.py`) queues items, runs them with the same `ensure_downloaded` and the server's shared `DownloadFlights`, and reports them as `DownloadItem`s. The routes:

| Route | Purpose |
|---|---|
| `GET /api/models/downloads` | The running item, the queued ones in order and recently finished ones |
| `GET /api/models/download/plan?kind=&name=` | The row's `label` and the job plan's shape (one part, its size, the free space and the licences); 404 for an unknown row, 424 when Hugging Face refuses (gated or missing repo; also from the planner on Windows and Linux), 503 when it cannot be reached |
| `POST /api/models/download` | Queue a row (`kind`, `name`); an already queued or running item for the row is returned; 424 when planning the row is refused by Hugging Face |
| `POST /api/models/downloads/{id}/cancel` | Remove a queued item or stop the running one |

**LoRA downloads.** The lane also runs items of kind `lora`: the Discover LoRAs **Download** button and **Use in LoRAs** switch, and the Models page's **Import a LoRA** from Hugging Face. They are not Models-page rows, so they start from their own routes (see [Discover LoRAs](web-server.md#discover-loras)), not from `POST /api/models/download`, but they appear in `GET /api/models/downloads` and are stopped by `POST /api/models/downloads/{id}/cancel` like any item, with the same `queued`, `running`, `done`, `failed` and `cancelled` states. `web/lora_download.py` builds an item:

- **Staged in a folder of its own.** The target is `DownloadTarget(repo, revision=<commit>, allow_patterns=(<file>,), local_dir=<loras>/.download-<name>)`, so the file never touches the Hugging Face cache and two files of one repo never share a flight. The folder sits beside the LoRA files so the final move is a rename on one drive. `web/lora_staging.py` holds a lock on a lock file inside the folder from the moment the item starts until its cleanup: `flock` on macOS and Linux (the way the temporary LoRA copies of `utils/lora_files.py` are locked), `msvcrt.locking` on Windows. `LoraInstaller.sweep_staging` (run when the server starts and before each new download) removes only the staging folders it can lock, so the leftovers of a killed server go while the folder of a download that another UI sharing the data folder is running stays; a download whose folder another UI holds fails instead of touching it. A folder that cannot be emptied (a file a virus scanner holds open, say) is left for a later sweep and the download stages in a fresh folder beside it.
- **Anonymous when it was not typed by the user.** A curated entry or a Discover file sets `DownloadTarget.anonymous`, and the check and the worker then pass `token=False`; the user's token is never sent, and a stale token cannot make a public file fail. **Import a LoRA** keeps the user's token, so a private repository they can open still imports.
- **Finalize, then cleanup.** `DownloadLane.submit(..., finalize=, cleanup=, extra=)` runs `finalize` on the lane thread once every target is on disk, and `cleanup` whatever the outcome. The LoRA `finalize` checks the staged file's size and SHA-256 against the curated entry or the Hub's `lfs.sha256` (`utils/lora_install.install_staged`), renames it to `<name>.safetensors` with one `os.replace` (refusing an existing file), and records its source in `lora_sources_v1` (for a Hugging Face file also the card's author, download count and licence, and its first preview image: see [LoRA sources](app-database.md#lora-sources)). A failed check, a stop or an error leaves nothing in the LoRA folder; `cleanup` removes the staging folder. The preview image is fetched after the item is done, on a thread of its own, and stored with `LoraSources.set_image`; any failure there is logged and ignored. Extra keys appear in the item JSON: `curated_id`, `source_repo`, `source_file`, `source_revision`, `size_bytes` and `anonymous` (false for an Import, which retries through the Import route with the user's login).
- **One decision at a time.** `LoraInstaller.start` decides the name and submits under one lock: the same curated entry or file pressed twice returns the running item, a curated entry whose file is already there counts as installed, an open file counts as installed when a `lora_sources_v1` row has its repository, file and SHA-256 and the file is on disk at the recorded size (under any local name, at any commit; `repo_rows` reads the rows once for a repository listing), a replaced file (same repository and file, other SHA-256) is a new version, and an open file whose name is taken gets `-2`, `-3`, and a curated name held by a different file or download is refused with `FileExistsError` (409) before any bytes download. `pending_sizes()` gives `{name: expected bytes}` of the LoRAs still downloading, which the MiniMax H3 memory estimate (`web/lora_fit.py`) counts until the file exists.
- **Queue order.** The lane runs one item at a time, so a LoRA waits behind a model download that is running.

The free-space figure is an estimate: it checks only the main download drive, counts shared xet blobs twice and ignores `HF_XET_CACHE`. The confirmation lets the user proceed anyway.

**Version bumps.** The planners depend on how the loaders choose files. After changing a pinned MLX LTX pack or `LTX_COMMIT`, re-list `mlx_files` as described under LTX on macOS in [Backends](backends.md#ltx-on-macos). After changing mflux, mlx-lm, diffusers, huggingface_hub or hf-xet, run the pattern pins (`tests/downloads/test_mac_download_plan.py` on macOS, which compare the planners with mflux's `get_download_patterns()` and mlx-lm's `DEFAULT_ALLOW_PATTERNS`; `tests/downloads/test_cuda_download_plan.py` on Linux, which pin the diffusers and CUDA video patterns against recorded file lists), and repeat the hand test with a small public repo: start a download from the Models page, check that progress moves, cancel mid-file, check that no `*.incomplete` remains and finished files stay, then start a job on the same model while the lane downloads it and check that Stop on the job leaves the download running. A renamed tqdm bar shows as progress stuck at 0 until each part completes, never as a failed download. A pattern that drifts only costs the progress display: the backend downloads the missing files during the load.
